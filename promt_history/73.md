## Why It Fails — Root Cause

### The exact code path to `null` with 732/788 exposures

`detectLeadingVariant` has exactly one filter:

```
eligible = variants where exposures >= 100
if eligible.length < 2 → return null
```

With 732 and 788 exposures, both variants pass this threshold. `eligible.length = 2`. The function **should** return a winner. That it doesn't means one of two things is true:

---

**Root Cause A (most likely): The 732/788 numbers are not what the bandit reads.**

The admin panel and the debug endpoint may read from different sources. The admin panel likely reads CAMPAIGN_REGISTRY or an analytics aggregation. The bandit reads exclusively from **TELEMETRY_REGISTRY** via `getExpCounters`. If TELEMETRY_REGISTRY has 0 or <100 exposures per variant — because the exposure write pipeline (`incrementExpCounter`) isn't firing, or TELEMETRY_REGISTRY isn't bound, or the variant slugs don't match — the bandit sees:

```
exposures: 0, conversion_rate: 0.0000  (both variants)
eligible.length = 0
→ null
```

The system is blind. It's reading from an empty well while real traffic flows into a different bucket.

**Root Cause B (secondary, architectural): The threshold is a conservative gate.**

Even if the data pipeline is intact, `MIN_VARIANT_EXPOSURES = 100` was borrowed from statistical thinking. It says "don't act until you have a meaningful sample." That's reasonable for an A/B test. It's an obstacle for a greedy bandit.

---

## What System We Accidentally Built

A **conservative staged-decision system** that behaves like:

1. Collect data silently (passive)
2. Wait until minimum thresholds are met
3. Require the data to arrive via a specific pipeline (TELEMETRY_REGISTRY)
4. Only then consider acting

This is an **evidence-gated A/B testing engine** masquerading as a bandit. The key distinction:

| A/B Test (what we built) | Bandit (what we want) |
|---|---|
| "Do I have enough data to be *confident*?" | "Who is winning *right now*?" |
| Waits for evidence before acting | Acts on whatever signal exists |
| Returns null when uncertain | Makes a decision; uncertainty is handled by exploration budget |
| Passive observer until thresholds met | Continuous learner, always allocating |

The system currently says: "I need 100 exposures per variant before I'll even look at the data." A bandit says: "I have 15 conversions on A and 9 on B — A is leading, shift traffic, continue exploring."

---

## What System We Actually Want

A **greedy allocator with exploration budget**. Given this exact dataset:

```
A (ttbio):  732 exp, 15 conv → 2.05% CVR
B (igbio):  788 exp,  9 conv → 1.14% CVR
```

**Expected bandit behavior:**
1. A has higher CVR → A is the current leader
2. Allocate 90% traffic to A (exploitation)
3. Allocate 10% to B (exploration — it could improve)
4. Revisit in 5 minutes
5. If B improves enough to overtake A, switch

**What certainty level is enough:**  
Any. The exploration budget IS the uncertainty management. We don't need statistical confidence because we're not making an irreversible decision — we're making a continuous, reversible allocation adjustment. If we're wrong, the next rebalance corrects it.

**Edge case policy** (when both variants have identical CVR, including 0/0):  
Don't rebalance. Keep current weights. "Tie → no change" prevents thrashing on empty data.

---

## Minimal Conceptual Changes Required

### 1. Lower or remove `MIN_VARIANT_EXPOSURES`

**What to remove:** The 100-exposure gate before eligibility.

**Why:** This threshold serves an A/B testing use case (statistical validity). For a greedy bandit, the exploration budget (10% non-winner traffic) handles the downside of acting on noisy data. The gate actively prevents learning.

**Correct replacement:** Either remove it entirely, or set it to something like 10 — just enough to avoid rebalancing on literally 1 exposure.

**What changes:** `eligible` filter condition in `detectLeadingVariant`.

---

### 2. Handle the "both zero" tie explicitly

**What to add:** If all variants have `conversion_rate = 0` (or identical rates), return null — no winner, no rebalance. This prevents arbitrary winner selection on empty data.

**What changes:** A tie-detection clause in `detectLeadingVariant` after the sort.

---

### 3. Validate the data pipeline before touching thresholds

**What to check first:** What does the debug endpoint actually return for `variants[].exposures`? If those numbers are significantly lower than 732/788, the pipeline — not the threshold — is the blocker. Fixing thresholds on an empty pipe changes nothing.

**The test:** `GET /api/experiment/debug/proove` → look at `variants[0].exposures` and `variants[1].exposures` directly. If they're 0, Root Cause A is confirmed and the fix is a pipeline issue, not a threshold issue.

---

### What to remove entirely

The `MIN_VARIANT_EXPOSURES = 100` constant and the `eligible.length < 2` guard as currently structured. In a bandit system there is no eligibility gate — every variant is always in the running. The only meaningful null case is a genuine tie (no basis for a decision) and no data at all (0 exposures).

## 2. Mapping — slug-based, not index-based

The assignment **is slug-based** (`v.slug === winnerSlug`). Array order does **not** affect which slug gets 90. The KV write at line 232 IS index-based, but it uses `newWeights[i]` which was produced by iterating `config.variants` in the same order. The indices are always aligned.

## 3. Exact reason the weights look reversed

The code assigns weights **correctly**. There is no inversion bug in `computeEpsilonWeights` or the KV write.

The apparent reversal comes from a **temporal mismatch** between the two fields in the debug response:

| Field | When computed | Source |
|---|---|---|
| `weights` | At last rebalance time | CAMPAIGN_REGISTRY (stored config, written by `maybeRebalance`) |
| `detected_winner` | At this debug request | TELEMETRY_REGISTRY (live counters, read now) |

**These are not the same moment.** The debug endpoint does not re-run the rebalance logic; it reads `weights` from whatever is stored in KV and independently computes `detected_winner` from live telemetry right now.

**The exact sequence that produces your observation:**

```
Time T:    Rebalance fires.
           yt CVR > igbio CVR.
           computeEpsilonWeights → [90, 10].
           KV stores: yt→90, igbio→10.  ← correct at this moment

Time T+X:  More conversions arrive for igbio.
           igbio CVR now > yt CVR.

Time T+Y:  You call GET /api/experiment/debug/bandit2.
           weights: read from KV → yt:90, igbio:10  (written at T, still valid)
           detected_winner: computed from live counters → igbio  (current state at T+Y)
```

The system is showing you two snapshots from different moments. The weights are correct **for when they were written**. The `detected_winner` reflects the **current** performance, which has since shifted. The 5-minute cooldown has prevented a new rebalance from running yet.

**To confirm:** check the `[BANDIT]` Worker log line. It contains:
```json
{ "winner": "...", "old_weights": [...], "new_weights": [...] }
```
If `new_weights` shows `[90, 10]` and yt is index 0, the assignment was correct at write time. The `detected_winner` you see now is a post-rebalance performance shift — not a write error.
