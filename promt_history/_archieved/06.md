#### 4. Root Cause of `route_fail_unknown_alias`

**Why `/atlas` fails even though `alias:atlas → atlas-release` exists in ALIAS_REGISTRY:**

```
resolveAlias("atlas")
  → ROUTE_TABLE.get("route:atlas") → null
  → route_fail_unknown_alias   ← runtime correctly reports miss
```

ROUTE_TABLE is empty for `route:atlas` because `compileRoutes()` **Phase A silently failed** for every campaign alias:

```
compileRoutes() Phase A (OLD):
  1. list ALIAS_REGISTRY → finds alias:atlas = "atlas-release"  ✓
  2. CR.get("campaign:atlas-release")                           ← CAMPAIGN_REGISTRY read
  3. CAMPAIGN_REGISTRY is always empty → returns null           ✗
  4. errors.push("missing campaign record: atlas-release")
  5. errors.length > 0 → abort write → ROUTE_TABLE never updated
```

**Why CAMPAIGN_REGISTRY is always empty:**
It was designed for a richer campaign schema with `{ campaign_id, default_channel, channels, modifier_map }`. No API ever wrote to it. All campaign data is stored in `LINKHUB_CAMPAIGNS` with the simpler schema `{ name, alias, isActive, createdAt }`. The namespace was bound in `wrangler.toml` but permanently empty.

**Why Phase B (slug aliases) worked but campaigns didn't:**
Phase B reads only `ALIAS_REGISTRY slug_alias:*` → validates against `LINKHUB_SLUGS`. Both are populated. No CAMPAIGN_REGISTRY dependency.

### PART 2 — ROUTING MODEL DECISION

**Architecture: compile-based. Confirmed correct.**

```
ALIAS_REGISTRY  ──→  compileRoutes()  ──→  ROUTE_TABLE  ──→  runtime
(write at save)         (ops action)       (compiled index)   (read-only)
```

**Why ROUTE_TABLE exists:**
- O(1) flat KV lookup at runtime — no alias graph traversal on hot path
- Workers Cache layer on top → sub-millisecond warm reads
- Immutable from the UI perspective: only `POST /api/admin/compile-routes` writes it
- Atomic compilation: all-or-nothing (error = no write → safe)

**Why ALIAS_REGISTRY is not read directly at runtime:**
- Prevents partial/inconsistent alias resolution across edge nodes
- Decouples alias management from routing availability
- Allows dry-run validation before activating new routes

**Correct workflow:**
```
1. Add/edit alias in UI (writes ALIAS_REGISTRY)
2. POST /api/admin/compile-routes  (reads ALIAS_REGISTRY + LINKHUB_SLUGS → writes ROUTE_TABLE)
3. routing active
```

### PART 5 — CLEAN ARCHITECTURE

#### CAMPAIGN_REGISTRY — Legacy, safe to retire

**Status:** Bound in `wrangler.toml`, never written, now no longer read.

**Why it existed:** Original architecture planned for a richer campaign structure:
```json
{
  "campaign_id": "atlas-release",
  "default_channel": "igbio",
  "channels": ["igbio", "youtube", "spotify"],
  "modifier_map": { "ig": "igbio", "yt": "youtube" }
}
```
This would have enabled modifier-based routing (`/atlas/yt` → `atlas-release-youtube`). That design was never implemented.

**Current state:** LINKHUB_CAMPAIGNS is the authoritative campaign store. It uses a simpler schema. The modifier_map concept is not exposed in the UI.

**Recommendation:** Remove the `CAMPAIGN_REGISTRY` binding from `wrangler.toml` when confirmed unused. Until then, the namespace is harmless — it's bound but no code reads or writes it.

#### `channelExists()` helper — Removed

Was only used by old Phase A (CAMPAIGN_REGISTRY channel validation). Not needed in new architecture. Removed from `route-compiler.js`.

#### `extractCampaignId()` → renamed `extractCampaignName()`

Functionally identical. Renamed to reflect that the value is a campaign name (not a separate campaign_id concept). Retains backward-compat JSON parsing for any legacy format that stored `{ "campaign_id": "..." }`.

#### Modifier routing — not implemented

The old Phase A also wrote `route:<alias>@<modifier>` entries using `modifier_map`. This is not implemented in the new Phase A (no modifier_map in LINKHUB_CAMPAIGNS). The `parsePath()` and `buildRouteKey()` in `alias-router.js` support modifiers at the routing layer — they are future-ready. No modifier routes are written to ROUTE_TABLE currently.
