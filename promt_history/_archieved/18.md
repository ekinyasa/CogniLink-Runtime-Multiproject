

## Campaign OS – Prompt 18.md

Goal

Stabilize diagnostics, fix incomplete UI behaviors introduced in Prompt 17, and complete the transition toward a fully autonomous self‑testing Campaign OS.

Prompt 17 introduced fixture‑based testing, health checks, hub validation and test campaign isolation. Core infrastructure works correctly, but several diagnostics and UX behaviors remain incomplete or inconsistent.

Prompt 18 resolves those gaps.

Important rules:

• Do NOT modify router logic.
• Do NOT modify analytics schema.
• Do NOT modify existing campaign routing behavior.
• Changes must remain backward compatible.

--------------------------------------------------

PART 1 — Replace Legacy Manual Validation With Fixture Validation

The existing "Manual Validation" still fires legacy traffic:

/nb
/nb
/nb/offer
/nb/vsl

This is inconsistent with the new fixture‑based system test.

Update manual validation so it:

1. Generates a fixture campaign identical to the system test.
2. Uses aliases containing the keyword "test".
3. Fires the deterministic click sequence:

/test
/test
/test/offer
/test/vsl

4. Validates analytics events using fixture‑scoped filters:

alias = fixture_alias
campaign = fixture_campaign

Expected events:

alias >= 4
offer >= 1
vsl >= 1

Manual validation must now reuse the same fixture creation logic used by the system tester.

--------------------------------------------------

PART 2 — Diagnostics Panel Must Display Fixture Metadata

The system test response already includes:

fixture: {
  alias,
  campaign
}

Update the diagnostics UI so the system test results panel shows:

Fixture Campaign
Fixture Alias
Fixture Slug

Example display:

Fixture Campaign: test-1772898554747
Fixture Alias: test-8d142b
Fixture Slug: test-1772898554747-igbio

This helps operators verify analytics results visually.

--------------------------------------------------

PART 3 — Fix Analytics "Show Test Campaigns" Filter UX

The current implementation filters only the campaign summary table.

Extend the filter to apply to ALL analytics panels:

1. Campaign table
2. Clicks by alias
3. Clicks by slug
4. Recent events table

Behavior rules:

When "Show test campaigns" is OFF:

• Hide all campaigns containing the keyword "test".
• Hide aliases containing "test".
• Hide slugs containing "test".

When "Show test campaigns" is ON:

• Show ONLY campaigns containing "test".

Recent events must follow the same filtering rules.

--------------------------------------------------

PART 4 — Admin Overlay Testability

Admin overlay currently requires a live alias route.

However fixture aliases are archived immediately after testing.

Add a diagnostics overlay test mode:

/admin/verify/<alias>?token=ADMIN_TOKEN

This endpoint should:

Render the hub page for the alias
Execute link validation
Show overlay indicators

This allows admin verification even after fixture cleanup.

--------------------------------------------------

PART 5 — Improve Hub Link Validation

Extend the existing link validator to check:

1. HTTP reachability
2. Redirect loops
3. Destination domain mismatch
4. Unexpected redirect chains

Return validation states:

VALID
SUSPICIOUS
BROKEN

Diagnostics UI should render the result with:

✔ VALID
⚠ SUSPICIOUS
✖ BROKEN

--------------------------------------------------

PART 6 — Continuous Background Self‑Testing

Introduce an optional background diagnostics task.

When enabled, Campaign OS should periodically run a lightweight system test using fixtures.

Recommended interval:

Every 6 hours

Behavior:

• Generate fixture campaign
• Fire deterministic click sequence
• Validate analytics ingestion
• Archive fixture

Results should be logged internally but not shown to normal users.

Diagnostics panel may display the timestamp of the last successful background test.

Example:

Last automatic system test: 2026‑03‑08 02:14 UTC

--------------------------------------------------

PART 7 — Expected Outcome

After implementing Prompt 18:

Campaign OS will provide:

• unified fixture‑based testing
• complete analytics filtering UX
• visible fixture metadata in diagnostics
• reliable admin overlay verification
• improved link validation
• optional background system self‑tests

At this stage Campaign OS becomes capable of:

self‑testing during runtime
continuous operational verification
safe diagnostics without contaminating production analytics

This completes the autonomous diagnostics layer of Campaign OS.
