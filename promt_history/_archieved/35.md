# Prompt 35 — Sticky Cookie Bucketing (Deterministic A/B Routing)

## Objective
Introduce **sticky bucketing** so that a visitor who enters an experiment is always routed to the **same variant across page reloads and future visits**. This prevents experiment contamination and ensures reliable attribution of clicks and conversions.

The routing logic must remain **O(1)** and must **not change the public routing grammar**.

Current public grammar (unchanged):

```
/<alias>
/<alias>/<modifier>
```

The experiment engine currently assigns variants randomly on each request. After this prompt, assignment must be **persistent per visitor**.

---

# Core Concept

A visitor entering an experiment receives a cookie identifying the chosen variant.

Subsequent requests:

```
request → cookie present → same variant
request → no cookie → assign variant → set cookie
```

This produces deterministic routing for repeat visitors.

---

# Cookie Design

Cookie name:

```
exp_<experimentAlias>
```

Example:

```
exp_abtest=cd26-test-yt
```

Cookie attributes:

```
Path=/
Max-Age=2592000   (30 days)
SameSite=Lax
Secure
```

Multiple experiments must coexist without conflict because each experiment uses its own cookie name.

---

# Routing Algorithm

When an alias request arrives:

1. Load experiment config
2. Check for cookie
3. If cookie matches a valid variant → use it
4. If no cookie → assign variant using weight distribution
5. Set cookie for the chosen variant

Pseudo-flow:

```
if (experimentActive) {

  cookieVariant = readCookie("exp_<alias>")

  if (cookieVariant && variantExists(cookieVariant)) {
      variant = cookieVariant
  } else {
      variant = weightedRandomVariant()
      setCookie("exp_<alias>", variant)
  }

}
```

---

# Determinism Requirements

The system must guarantee:

- same visitor → same variant
- repeat visits → same variant
- experiment stats remain valid

Sticky bucketing must apply only when an experiment exists for the alias.

If no experiment exists, routing remains unchanged.

## 1. Cookie Schema

Name:    `exp_<alias>`  (e.g. `exp_abtest`)
Value:   selected variant slug  (e.g. `cd26-test-yt`)
Attributes:  Path=/; Max-Age=2592000 (30 days); SameSite=Lax; Secure

Multiple experiments coexist without conflict — each alias gets its own
cookie name. `buildSetCookie()` in cookie-utils.js constructs the full
header string. All attributes are configurable via an options object.

---

## 2. cookie-utils.js

Two pure, dependency-free helpers:

`readCookie(request, name)`
  • Reads the "cookie" request header, splits on ";" to find key=value
  • Returns the value string or null — O(1), no KV reads, no async

`buildSetCookie(name, value, opts)`
  • Builds a valid Set-Cookie header value string
  • Defaults: Max-Age=2592000, Path=/, SameSite=Lax, Secure=true

---

## 3. Sticky Bucketing Algorithm (functions/[[path]].js)

When an A/B config exists for the alias:

  1. Read cookie: readCookie(request, "exp_" + alias)
  2. Validate against abConfig.variants[].slug (validSlugs array)
  3a. Cookie valid → finalSlug = cookieVariant; newAssignment = false
  3b. No/invalid cookie → finalSlug = selectABVariant(); newAssignment = true

selectABVariant() is called ONLY on first visit (no valid cookie).
Returning visitors bypass weight distribution entirely — pure O(1) lookup.

ab_selected ops event gains detail.sticky: true for returning visitors
(queryable for separating new vs. returning participants).

Exposure counter still increments on every page view regardless of sticky
status — each render is a valid exposure event.

---

## 4. Response Headers

Uses a Headers object (not plain object) to safely append Set-Cookie.

Cache-Control strategy:
  • adminVerified          → no-store  (unchanged)
  • newAssignment = true   → no-store  (prevents caching the cookie-setting
                             response for delivery to different visitors)
  • returning visitor      → public, max-age=60, s-maxage=0  (unchanged)

Set-Cookie appended only when newAssignment = true.

---

## 5. Safety

Cookie value validated against live A/B config before use.
If stored slug no longer exists in config (variant removed), cookie is
ignored and a fresh assignment is made. No stale routing possible.
