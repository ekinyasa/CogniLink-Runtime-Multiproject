

# Prompt 46 — Campaign OS Stabilization (Polish Phase)

We are entering the stabilization phase of the Campaign OS attribution engine.

Core routing, exposure tracking, and conversion logging are working correctly.
The goal of this prompt is to improve developer ergonomics, operational safety, and analytics robustness without altering the fundamental routing logic.

This prompt introduces four improvements:

1. Convert endpoint experiment resolution fallback
2. Experiment status lifecycle (open / decided)
3. Router fast‑path for decided experiments
4. KV analytics key distribution fix (prevent hot‑key concentration)

No behavior should change for existing running experiments.

---

## 1. Convert Endpoint — Experiment Resolution Fallback

Currently the `/api/convert` endpoint requires:

experiment = alias
variant = slug

Example:

experiment = abrand45
variant = ab-rand-45-igbio

However users often send the campaign name instead of the alias:

experiment = ab-rand-45

This results in `experiment_not_found`.

### Convert endpoint resolution flow

incoming experiment parameter
↓
check KV: ab_config:<experiment>
↓
if exists → treat as alias
↓
if not found:
    lookup campaign registry
    where campaign.name == experiment
↓
resolve alias
↓
continue processing

Both payloads must work:

experiment = abrand45
experiment = ab-rand-45

If neither lookup resolves:

return experiment_not_found

This improves debugging and prevents unnecessary failures.

---

## 2. Experiment Status Lifecycle

Introduce a status field inside experiment configuration.

Current config example:

ab_config:<alias>
{
  "variants": [...]
}

New structure:

ab_config:<alias>
{
  "status": "open",
  "variants": [...]
}

Possible states:

open
decided

When an experiment winner is chosen:

{
  "status": "decided",
  "winner": "variant-slug"
}

Existing experiments without this field should default to:

status = open

---

## 3. Router Fast Path (Decided Experiments)

Router must detect decided experiments and bypass random routing.

Pseudo logic:

load ab_config

if status == decided
    return winner

else
    perform weighted random routing
    record exposure

Benefits:

- eliminates unnecessary KV writes
- prevents analytics pollution after decision
- reduces router CPU work
- stabilizes campaign routing

Exposure counters must NOT increment when status = decided.

---

## 4. KV Analytics Key Distribution Fix

Current analytics keys concentrate traffic on a small number of KV keys.

Example:

exp:<experiment>:<variant>:exposure
exp:<experiment>:<variant>:conversion

Under load this creates hot keys.

Introduce sharded counters.

New format:

exp:<experiment>:<variant>:exposure:<shard>
exp:<experiment>:<variant>:conversion:<shard>

Shard selection:

shard = random integer 0‑7

Example keys:

exp:abrand45:ab-rand-45-igbio:exposure:3
exp:abrand45:ab-rand-45-igbio:conversion:6

Panel aggregation must sum all shards.

Aggregation logic:

for shard in 0..7
   read counter
   sum results

For backward compatibility the system should also read legacy non‑sharded keys if they exist.

---

## Safety Requirements

Do NOT change:

- routing URLs
- experiment KV naming
- variant slug format
- campaign registry schema

All improvements must remain backward compatible.

---

## Expected Result

• convert endpoint accepts alias OR campaign name
• experiments support lifecycle states
• router bypasses decided experiments
• analytics writes distribute across KV shards
• system becomes production‑safe without changing routing behavior

## Section 1 — Convert Endpoint Experiment Resolution Fallback

`/api/convert` now resolves the `experiment` parameter in two steps:

**Step 1 — Direct alias lookup** (existing):
```js
let abConfig = await loadABConfig(expAlias, env);
```

**Step 2 — Campaign name fallback** (new — only triggered on miss):
```js
const listed = await env.ALIAS_REGISTRY.list({ prefix: "ab_config:" });
for (const { name: key } of listed.keys) {
  const candidate = await env.ALIAS_REGISTRY.get(key, { type: "json" });
  const derived   = deriveCampaignFromSlug(candidate.variants[0].slug);
  if (derived === expAlias) {
    resolvedAlias = key.slice("ab_config:".length);
    abConfig      = candidate;
    break;
  }
}
```

`deriveCampaignFromSlug("ab-rand-45-igbio")` → `"ab-rand-45"`, so sending `experiment: "ab-rand-45"` now correctly resolves to alias `abrand45`. Counter writes and logs use `resolvedAlias`. When a fallback was used, `experiment_input` is added to the log line for traceability.

Both payloads now work:
```json
{ "experiment": "abrand45",  "variant": "ab-rand-45-igbio", "event": "signup" }
{ "experiment": "ab-rand-45","variant": "ab-rand-45-igbio", "event": "signup" }
```

## Section 2 — Experiment Status Lifecycle

Introduces `status: "open" | "decided"` alongside `state: "RUNNING"|"PAUSED"|"DECIDED"|"ARCHIVED"`.

`state` always takes precedence. `status` is a backward-compat fallback for configs without a `state` field:

```js
// ab-router.js getExpState
if (typeof s === "string" && EXP_STATES.includes(s)) return s;   // state wins
if (config.status === "decided") return "DECIDED";               // status fallback
return "RUNNING";
```

- **`api/ab.js` PUT**: new configs get `status: "open"`; existing status preserved on update
- **`persistDetectedWinner`**: sets `status: "decided"` alongside `state: "DECIDED"`
- **`/api/experiments` response**: `status` derived from `effectiveState` — `"decided"` when DECIDED or ARCHIVED, `"open"` otherwise
