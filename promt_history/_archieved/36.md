# Prompt 36 — Experiment Analytics UI (Clarity‑First Dashboard)

## Objective
Create a lightweight **Experiment Analytics Dashboard** that makes experiment outcomes understandable at a glance.

The first screen must communicate the *state of the test instantly* before showing detailed analytics.

Design principle:

```
clarity first
analysis second
```

The interface must remain **minimal, dependency‑light, and fast**.

Charts may use a **small open‑source library (recommended: Chart.js)** but the UI itself must remain **vanilla JS + HTML**.

---

# Route

Create a new admin analytics route:

```
/admin/experiments
```

This page reads experiment data from:

```
/api/experiments
```

The UI must remain fully **client‑side rendered**.

---

# Dashboard Layout

The analytics page has **four layers of information**.


---------------------------------
LAYER 1 — Instant Experiment State
---------------------------------

The first screen communicates the current state of the experiment.

Display:

```
Experiment: <alias>
Status: RUNNING / EARLY / DECIDED
Traffic: <total exposures>
Winner: <variant slug or none>
Confidence: <low / medium / high>
```

Status logic:

```
if exposures < MIN_EXPOSURE
    → EARLY

if winner detected
    → DECIDED

else
    → RUNNING
```

Visual cues:

```
green   → winner clear
orange  → running
gray    → early
```

The user should instantly feel one of these:

```
"winner is obvious"
"test still running"
"too early"
```

No scrolling required to understand the state.

---


---------------------------------
LAYER 2 — Variant Performance Table
---------------------------------

Display a compact comparison table.

Columns:

```
Variant
Traffic (exposures)
Clicks
Conversions
Conversion Rate
Lift vs Baseline
```

Example:

```
Variant        Traffic   Clicks   Conv   Rate    Lift
------------------------------------------------------
IGBio          600       90       12     2.0%    baseline
YouTube        620       110      24     3.9%    +95%
```

Formatting rules:

```
winner row → highlight green
baseline → neutral
losing variants → muted
```

Conversion Rate formatting:

```
(rate * 100).toFixed(2) + "%"
```

Lift calculation:

```
(variantRate − baselineRate) / baselineRate
```

Display as percentage.

---


---------------------------------
LAYER 3 — Conversion Trend Chart
---------------------------------

Add a simple line chart showing experiment progress.

Chart:

```
conversion rate over time
```

X‑axis:

```
request sequence or timestamp bucket
```

Y‑axis:

```
conversion rate
```

Recommended implementation:

```
Chart.js
```

Reasons:

```
MIT license
small footprint
simple setup
widely used
```

Chart must render only if enough data exists.

If data is insufficient:

```
"Not enough data yet"
```

---


---------------------------------
LAYER 4 — Expandable Advanced Metrics
---------------------------------

Below the primary analytics, include an expandable section:

```
Advanced Analytics
```

Collapsed by default.

Potential metrics:

```
device
screen size
referrer
country
campaign origin
```

These metrics must **not slow the core dashboard**.

The system should remain flexible so additional breakdowns can be added later without restructuring the experiment engine.

Rule 1 — Immediate clarity

When the page loads, the user should immediately feel:


# Summary — Prompt 36 Implementation

## Files created

### `functions/admin/experiments.js`
New Cloudflare Pages route that serves the experiment analytics dashboard at `/admin/experiments`.

The page is fully client-side rendered with the same localStorage `admin_token` gate as the main admin panel. On load it:
1. Reads `admin_token` from localStorage — shows a token gate if absent.
2. Fetches the alias list from `GET /api/admin/aliases` to populate a selector dropdown.
3. On **Load**, calls `GET /api/experiments?alias=<alias>` (Bearer token) and renders all four layers.

**Layer 1 — Instant Experiment State**

A status card with three visual states:

| State | Colour | Condition |
|---|---|---|
| `EARLY` | neutral/gray | any variant below `MIN_EXPOSURE` (30) |
| `DECIDED` | green | `winner !== null` |
| `RUNNING` | orange | exposure ≥ threshold, no winner yet |

Displays: experiment alias · total traffic · winner slug · confidence (low/medium/high) · variant count. No scrolling required to understand the current state.

**Layer 2 — Variant Performance Table**

Columns: `Variant | Traffic | Clicks | Conv. | Conv. Rate | Lift vs Baseline`

- Winner row → green background + left border + "Winner" pill badge
- Baseline row → neutral opacity
- Losing rows → reduced opacity
- Lift: uses `conversion_lift` if present, falls back to CTR-based `lift`; formatted as `+X.X%` (green) or `-X.X%` (red)

Conversion rate: `(rate × 100).toFixed(2) + "%"`

**Layer 3 — Conversion Rate Bar Chart (Chart.js)**

Since the KV store holds only cumulative counters (no time-series), the chart is a **grouped bar chart** comparing variant metrics at the current snapshot:
- Primary bars: Conv. Rate (%) — winner bar highlighted green
- Secondary bars: CTR (%) — muted
- Respects `prefers-color-scheme` for dark mode colours
- Hidden with "Not enough data yet" message if no variant has reached `MIN_EXPOSURE`
- Chart.js loaded from CDN (`cdn.jsdelivr.net`, MIT licence, `@4.4.2`)

**Layer 4 — Advanced Analytics (collapsed)**

An expandable `<details>` section (collapsed by default) with five dimension tiles:
`Device · Screen Size · Referrer · Country · Campaign Origin`

Each tile shows "Not collected yet" — the architecture is ready for future KV breakdowns to be wired in without restructuring the experiment engine.

---

## Design decisions

- **Standalone page** (not a tab pane) keeps the experiments dashboard focused and avoids overloading the main panel's tab count.
- **No additional API endpoints** — the page reads from the existing `/api/experiments` and `/api/admin/aliases` endpoints as specified.
- **Min-dependency**: one external JS file (Chart.js CDN). The page itself is vanilla JS + HTML as required.
- **`Cache-Control: no-store`** on the HTML response prevents caching of the admin page.
- **Chart fallback**: if Chart.js fails to load from CDN, `typeof Chart === 'undefined'` check shows the "Not enough data yet" fallback gracefully.
