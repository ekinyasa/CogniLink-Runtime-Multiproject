Campaign OS – Prompt 17.md

Goal

Extend Campaign OS with stronger observability and fully autonomous system testing. The system should be able to create and validate its own isolated test campaigns without affecting production data, while also improving operational visibility.

Important rules:

• Do NOT modify the router logic.
• Do NOT modify the analytics schema.
• All new logic must remain compatible with existing diagnostics and admin UI.
• All test artifacts must be clearly isolated from production campaigns.

--------------------------------------------------

PART 1 — Health Endpoint

Implement a new endpoint:

/api/admin/health

Purpose:

Provide a lightweight operational status endpoint that can be used by monitoring tools or uptime checks.

Response example:

{
  "ok": true,
  "router": "ok",
  "kv": "ok",
  "analytics": "ok",
  "deployment": "<deployment-id>",
  "version": "<git-or-build-id>",
  "timestamp": "<server-time>"
}

Checks performed:

Router health
KV availability
Analytics write capability

The endpoint must execute quickly and avoid long retries.

--------------------------------------------------

PART 2 — Fixture-Based Isolated Test Campaign Creation

Extend the system tester so it can create an isolated test campaign automatically.

When a system test runs:

Generate a unique test campaign identifier:

Example:

campaign: test-<timestamp>
alias: test-<shortid>
slug: test-<timestamp>-fixture

These values must:

Contain the keyword "test"
Never collide with production aliases
Be clearly identifiable as test data

The system test should then perform a deterministic request sequence:

/test
/test
/test/offer
/test/vsl

This sequence replaces the previous nb-based diagnostics traffic.

--------------------------------------------------

PART 3 — Fixture-Specific Analytics Filtering

All analytics validation queries must be scoped to the generated test campaign.

Example filters:

alias = generated_test_alias
campaign = generated_test_campaign

This ensures:

Production campaign traffic does not affect test results.

--------------------------------------------------

PART 4 — Automated Cleanup / Archive

After the test completes:

The generated test campaign must be automatically archived.

Implementation options:

Mark slug as archived
or move to test-only namespace

Archived test campaigns should:

Remain queryable for diagnostics
Not appear in normal campaign lists

--------------------------------------------------

PART 5 — Stronger Per-Link Validation

Improve hub integrity validation beyond simple reachability.

Each hub link should be validated for:

HTTP reachability
Correct destination domain
Redirect chain validity
Correct override usage

Validation result example:

✔ VALID
⚠ SUSPICIOUS
✖ BROKEN

Diagnostics UI should display the validation state next to each link.

--------------------------------------------------

PART 6 — Admin-Only Continuous Hub Verification

Add an admin-only verification mode.

When an admin loads a hub page:

Each link should display a validation indicator.

Example:

✔ link verified
✖ broken link
⚠ unexpected redirect

This must only appear for authenticated admin users.

Normal visitors must not see verification indicators.

--------------------------------------------------

PART 7 — Diagnostics Test Alias Naming

Replace existing diagnostics aliases such as:

nb
nb/offer
nb/vsl

with aliases containing the keyword "test".

Example:

/test
/test/offer
/test/vsl

This clearly separates diagnostics traffic from real campaign traffic.

--------------------------------------------------

PART 8 — Test Slug Filtering in Admin UI

Extend the admin UI filtering capabilities.

Test slugs must behave similarly to archived slugs.

Add a filter toggle:

"Show test campaigns"

When disabled:

Test campaigns are hidden from normal campaign lists.

When enabled:

Only test campaigns are shown.

Apply this filter to:

Campaign list
Campaign links list
Analytics campaign view

This allows operators to inspect diagnostics data without mixing it with real campaign analytics.

--------------------------------------------------

Expected Outcome

After implementing Prompt 17:

Campaign OS gains:

Health monitoring
Autonomous fixture-based testing
Isolated analytics verification
Automated cleanup of test data
Advanced link validation
Admin-only continuous hub verification
Test campaign filtering

The system will now be capable of performing full self-validation without operator involvement.
