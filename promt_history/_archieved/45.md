# Prompt 45 — Production Hardening (Routing + KV Safety)

Goal: Harden the Campaign OS experiment engine for high‑traffic production environments. This prompt addresses three critical failure modes discovered during testing and review:

1) KV hot‑key pressure
2) winner write race conditions
3) unnecessary experiment routing after winner decision

Only infrastructure‑level fixes are included here. No UI work and no analytics expansion.

---

# 1) KV Hot‑Key Mitigation (Sharded Counters)

Current exposure counters use a single key pattern:

exp:{experiment}:{variant}:exposure

Under high traffic this creates write contention and latency spikes because all requests increment the same KV key.

Replace with sharded counters:

exp:{experiment}:{variant}:exposure:{shard}

Where:

shard = random integer between 0–9

Write behavior:

• increment random shard
• shards distribute write load

Read behavior:

• aggregate exposure by summing all shards

Example keys:

exp:ab1:variantA:exposure:0
exp:ab1:variantA:exposure:1
exp:ab1:variantA:exposure:2
...

Admin panel and API must sum shards when computing exposure totals.

Purpose:

Prevent KV hot‑key contention under high request volume.

---

# 2) Winner Write Protection (CAS Guard)

Edge workers can evaluate winner logic simultaneously. Without protection two workers may write different winners.

Example race:

worker A → winner = variantA
worker B → winner = variantB

Add compare‑and‑set protection when writing the winner.

Rules:

• only write winner if no stored_winner exists
• if stored_winner exists → do not overwrite

Pseudo logic:

if stored_winner == null
  write stored_winner
else
  skip

This guarantees only the first winner decision persists.

---

# 3) Winner Fast‑Path Routing

After an experiment reaches DECIDED state the router should bypass the experiment engine.

Current behavior:

request
→ experiment engine
→ variant logic
→ winner override

Replace with fast‑path:

if experiment.state == DECIDED
  route directly to stored_winner

This removes unnecessary computation and reduces edge latency.

Attribution parameters must still be appended:

utm_experiment
utm_variant
utm_campaign
utm_source
utm_medium

Routing correctness must remain identical.

---

# 4) Experiment Metadata Backfill

Older experiments may have missing timestamps.

If created_at is null and decided_at exists:

created_at = decided_at

This ensures all experiments have usable lifecycle timestamps.

---

# Implementation Scope

This prompt affects:

• routing layer
• experiment API
• exposure counter storage

No UI changes.

## Section 1 — KV Hot-Key Mitigation (Sharded Counters)

### `exp-counter.js` — write side

```js
export const NUM_SHARDS = 10;

export async function incrementExpCounter(env, alias, slug, type) {
  const shard = Math.floor(Math.random() * NUM_SHARDS);
  const key   = `exp:${alias}:${slug}:${type}:${shard}`;
  // ... read-modify-write to sharded key
}
```

Each write picks a random shard `0–9`, distributing write load across 10 independent KV keys per metric. Under high traffic this reduces per-key write frequency by ~10×.

### `exp-counter.js` — read side

```js
export async function getExpCounters(env, alias, slugs, shardCount = NUM_SHARDS) {
  const readMetric = async (type) => {
    const keys = [
      `exp:${alias}:${slug}:${type}`,           // legacy unsharded key (backward compat)
      ...Array.from({ length: n }, (_, i) => `exp:${alias}:${slug}:${type}:${i}`),
    ];
    // parallel reads, sum all values
  };
}
```

Reads aggregate the legacy unsharded key (backward compat for pre-sharding data) + all `n` shards. All reads are parallel via `Promise.all`.

### `shard_count` stored in AB config (`api/ab.js`)

```js
import { NUM_SHARDS } from "../_shared/exp-counter.js";

const config = {
  variants:    body.variants,
  shard_count: existingConfig?.shard_count ?? NUM_SHARDS,
  created_at:  existingConfig?.created_at  ?? now,
  updatedAt:   new Date().toISOString(),
};
```

`shard_count` is persisted in the AB config so reads always aggregate exactly the right number of shards — even if `NUM_SHARDS` changes in a future deployment.

### `shard_count` used at read time (`api/experiments.js`)

```js
const shardCount = abConfig.shard_count ?? NUM_SHARDS;
const raw        = await getExpCounters(env, alias, slugs, shardCount);
```

Also exposed in the API response (`shard_count` field) for operator observability.

## Section 2 — Winner Write Protection (CAS Guard)

`persistDetectedWinner` in `api/experiments.js` already did a read-before-write and checked `if (current.winner) return;`. Section 2 makes the semantic explicit with a CAS comment:

```js
// CAS guard (Section 2 — Prompt 45):
// Only write the winner if no stored_winner exists yet.
// First writer wins — subsequent concurrent workers that also detected a
// winner (possibly a different one) will skip the write here, ensuring
// only one winner is ever persisted per experiment.
if (current.winner) return; // stored_winner already set — skip, first writer wins
```

True atomic CAS is not available in Workers KV; this read-then-skip pattern provides the closest approximation and is sufficient for typical campaign traffic volumes.

## Section 3 — Winner Fast-Path Routing

DECIDED branch in `[[path]].js` — removed `context.waitUntil(incrementExpCounter(...))` and `emitOps(AB_SELECTED, ...)`:

```js
// DECIDED fast-path: bypass counter writes
// Winner is fixed — no analytical value in continuing to write exposure counters.
// Attribution UTMs still appended (utm_experiment / utm_variant).
const decidedWinner = (typeof abConfig.winner === "string" && abConfig.winner)
  ? abConfig.winner : null;
finalSlug     = decidedWinner ?? canonicalSlug;
newAssignment = false;
utmExperiment = alias;
utmVariant    = finalSlug;
// ← no incrementExpCounter call
```

**Impact:** every request to a DECIDED experiment now saves one KV read + one KV write. At high traffic this is a significant latency reduction.

**Attribution preserved:** `utmExperiment` and `utmVariant` are still set, so all downstream hub links carry `utm_experiment` and `utm_variant` parameters. Conversion attribution is unaffected.

## Section 4 — Experiment Metadata Backfill

In `api/experiments.js` response:

```js
// Backfill: if created_at is null but decided_at exists, use decided_at
const createdAt = abConfig.created_at ?? abConfig.decided_at ?? null;
```

Older experiments created before Fix 1.5 (Prompt 44) may have `created_at: null`. Using `decided_at` as a fallback ensures analytics timelines and lifecycle dashboards have a usable anchor timestamp for all experiments.

## Design decisions

- **Backward compat via legacy key**: `getExpCounters` always reads the old unsharded key in addition to shards. Existing counter data is not lost; no migration required. Legacy key reads will gradually become zero as experiments are reset or replaced.
- **`shard_count` in config**: storing the shard count alongside the experiment config decouples the write-shard-count from the runtime constant. Future shard count changes can be applied per-experiment without breaking historical reads.
- **DECIDED counters removed**: once an experiment reaches DECIDED state, exposure counters serve no analytical purpose (the winner is already chosen). Removing the write eliminates the last remaining KV write from the DECIDED request path.
- **CAS is best-effort**: Workers KV does not support atomic compare-and-swap. The `read → check → write` guard reduces the race window to the KV propagation latency. For typical campaign volumes (< 1 k req/s) double-writes are extremely rare and self-correcting (both writers would set the same winner slug).
