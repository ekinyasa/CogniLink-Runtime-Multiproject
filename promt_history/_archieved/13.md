

Campaign OS – Claude Implementation Prompt (Smoke Test First Strategy)

Context

We already have a working Campaign OS stack deployed on Cloudflare Pages + Functions with:
- alias router
- modifier routing
- telemetry emission
- analytics ingestion (Analytics Engine)
- admin panel

There is currently a CLI-based test runner located under /tests/run-tests.js which runs router / modifier / telemetry / analytics checks from the terminal.

We now want to evolve testing in a safer order:

1) FIRST: internal **smoke test endpoint** inside Campaign OS
2) SECOND: admin panel **Diagnostics tab** that calls the smoke test
3) THIRD: optional CLI runner that simply calls the same endpoint

The goal is to avoid duplicated logic and ensure **one canonical test engine**.

--------------------------------------------------

Architecture Goal

Introduce a small internal test engine that can:

• simulate router hits
• verify telemetry emission
• verify analytics ingestion
• return structured diagnostics

without modifying production data.

This should run entirely from the server side (Workers environment).

--------------------------------------------------

Step 1 — Create Smoke Test Endpoint

Add a new endpoint:

/api/admin/smoke-test

Authorization:
Use existing ADMIN_TOKEN mechanism.

The endpoint should:

1) perform synthetic requests against the router

Example calls (using fetch internally):

GET /nb
GET /nb/offer
GET /nb/vsl

2) wait ≈700ms (AE ingestion buffer)

3) query Analytics Engine using the same dataset used by the admin analytics panel

4) derive the following results:

router_ok
modifier_routing_ok
telemetry_emit_triggered
analytics_ingestion_ok

Return JSON:

{
  ok: true,
  router: "pass",
  modifier: "pass",
  telemetry: "pass",
  analytics: "pass",
  duration_ms: number,
  warnings: []
}

If something fails, mark the section as "fail".

--------------------------------------------------

Step 2 — Internal Test Engine (shared module)

Create shared module:

/functions/_shared/test-runner.js

Expose:

runSmokeTests(env)

Responsibilities:

• perform router fetch tests
• verify telemetry presence
• verify analytics ingestion by querying recent alias_click events (last 5 minutes)
• collect timing
• produce structured report

This module should contain the core logic so it can be reused.

--------------------------------------------------

Step 3 — Admin Panel Diagnostics Tab

Add new tab in admin renderer:

Diagnostics

UI elements:

Run Smoke Test button

When clicked:

POST /api/admin/smoke-test

Display results:

Campaign OS Diagnostics

Router            PASS/FAIL
Modifier routing  PASS/FAIL
Telemetry ingest  PASS/FAIL
Analytics ingest  PASS/FAIL

Show duration and warnings.

--------------------------------------------------

Step 4 — CLI Runner Refactor

Modify the existing CLI runner (/tests/run-tests.js):

Instead of implementing its own logic, it should:

call:

POST /api/admin/smoke-test

and display the result.

This prevents duplicated test logic.

If necessary:

keep the CLI runner as a thin wrapper.

--------------------------------------------------

Step 5 — Safety Constraints

Smoke tests MUST:

• never mutate campaign registry
• never create new aliases
• never modify KV
• only simulate GET requests

All tests should use existing alias / slug combinations.

--------------------------------------------------

Step 6 — Expected Output

Smoke test response example:

{
  ok: true,
  router: "pass",
  modifier: "pass",
  telemetry: "pass",
  analytics: "pass",
  duration_ms: 420,
  warnings: []
}

Admin panel should render this cleanly.

--------------------------------------------------

Implementation Notes

Prefer minimal code changes.
Reuse existing router and analytics utilities wherever possible.
Do not refactor unrelated parts of the system.

Focus only on:

• smoke test endpoint
• shared test engine
• admin diagnostics tab
• CLI runner simplification

--------------------------------------------------

Goal

Campaign OS should gain a built-in system health test that can be triggered from the admin panel and optionally from CLI, without duplicating logic.

2 yeni dosya, 2 dosya güncellendi. Tek bir test engine — admin panel ve CLI aynı sunucu taraflı kaynaktan besleniyor.

### Mimari

```
functions/_shared/test-runner.js    ← tek kaynak: runSmokeTests(env, request)
        ↓
functions/api/admin/smoke-test.js   ← POST /api/admin/smoke-test  (server-side)
        ↓
functions/_shared/admin-renderer.js ← Diagnostics tab  (admin panel UI)
        ↓
tests/run-tests.js                  ← thin CLI wrapper  (sadece endpoint çağırır)
```

---

### Step 1 ✅ — `functions/_shared/test-runner.js` (YENİ)

`runSmokeTests(env, request)` export'u:

| Adım | Ne yapar |
|------|----------|
| 1. Router probe | `GET /nb` → 200 bekler |
| 2. Modifier probe | `GET /nb/offer`, `/nb/vsl` → 200 bekler (paralel) |
| 3. Telemetry wait | 400ms bekler (AE ingestion için) |
| 4. AE query | Son 5 dakikada `alias_click` event var mı? |

**Tasarım kararları:**
- `new URL(request.url).origin` → base URL türetilir, `CAMPAIGN_OS_BASE_URL` env var gerekmez
- Telemetry "pass" = trigger istekleri başarılı (single-request cycle içinde AE write-through doğrulaması mümkün değil)
- AE credentials yoksa warnings'e not düşer, testi kesmez
- Read-only güvenlik kuralları kod içinde belgelenmiş
- Router requests MUST derive base URL from request.origin (e.g. new URL(request.url).origin) Do NOT hardcode any domain.

---

### Step 2 ✅ — `functions/api/admin/smoke-test.js` (YENİ)

`POST /api/admin/smoke-test` (GET da destekleniyor — browser kolaylığı için)

- Mevcut `verifyToken` + `unauthorized()` auth mekanizması kullanıldı
- `runSmokeTests(env, request)` çağırır, sonucu JSON olarak döner
- HTTP status her zaman 200 — `ok` field sağlık sinyali taşır
- Beklenmedik throw durumunda 500 döner

---

### Step 3 ✅ — Diagnostics tab (`functions/_shared/admin-renderer.js`)

Tab bar'a "Diagnostics" eklendi (Routing'den sonra, son tab):

```
Analytics | Campaign Links | Campaigns | Hub Config | Routing | Diagnostics
```

**Tab içeriği:**
- "Run Smoke Test" butonu (manuel tetiklemeli — auto-load yok)
- Router / Modifier routing / Telemetry ingest / Analytics ingest satırları (✓ PASS / ✖ FAIL)
- Duration + genel sonuç meta satırı
- Warnings listesi (sarı, sadece varsa gösterilir)

**JS eklentileri:**
- `diagnosticsTabLoaded` flag (gelecek genişletme için ayrıldı)

- `diagLabel(value)` — renkli ✓ PASS / ✖ FAIL span üretici
- `runDiagnostics()` — buton disabled/enabled yönetimi, API çağrısı, render
- Mevcut `apiFetch` helper'ı ile auth otomatik ekleniyor
