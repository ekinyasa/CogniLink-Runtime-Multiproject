

# Prompt 40 — False Winner Guardrails

## Problem

Current experiment lifecycle:

RUNNING → WINNER DETECTED → DECIDED → 100% ROUTING

This is fast but statistically fragile. A small or noisy sample can produce a **false winner**.

Typical failure scenarios:

- Early spike in conversions
- Small sample size
- Traffic bursts from a single source
- Conversion clustering from the same session
- Short experiment runtime

Example:

Variant A: 12 exposures / 2 conversions  
Variant B: 11 exposures / 0 conversions  

Conversion rate:

A = 16.6%  
B = 0%

The system might prematurely declare A as the winner even though the sample size is meaningless.

---

## Goal

Introduce **guardrails before declaring DECIDED**.

Winner detection should require **minimum statistical conditions**.

The experiment engine must only transition:

RUNNING → DECIDED

when safety thresholds are satisfied.

---

## Guardrails

### 1. Minimum Sample Size

Each variant must reach a minimum number of exposures.

Example rule:

```
min_exposures_per_variant = 30
```

Winner detection must be blocked if any variant is below this threshold.

---

### 2. Minimum Runtime

Experiments should run long enough to avoid time‑based bias.

Example rule:

```
min_runtime_minutes = 60
```

Compute:

```
now - experiment.created_at
```

If runtime is below the threshold → remain RUNNING.

---

### 3. Minimum Conversion Gap

A meaningful difference between variants must exist.

Example rule:

```
min_conversion_rate_gap = 0.03
```

Meaning a **3 percentage point difference** between variants.

Example:

```
A = 5.0%
B = 3.2%
gap = 1.8% → not enough
```

---

### 4. Minimum Conversions

Prevent decisions based on tiny conversion counts.

Example rule:

```
min_total_conversions = 5
```

If total conversions across variants are below this → block decision.

---

## Decision Logic

Replace current winner detection logic with guarded evaluation:

```
if exposures_per_variant < min_exposures_per_variant:
    state = RUNNING

else if runtime < min_runtime_minutes:
    state = RUNNING

else if total_conversions < min_total_conversions:
    state = RUNNING

else if conversion_gap < min_conversion_rate_gap:
    state = RUNNING

else:
    state = DECIDED
    stored_winner = best_variant
```

---

## Why This Matters

Without guardrails:

- experiments end too early
- random noise produces winners
- traffic is routed to a bad variant
- attribution data becomes misleading

With guardrails:

- experiments stabilize
- decisions are reproducible
- analytics become trustworthy

---

## Expected Behaviour

Before guardrails:

```
exposures = 12
conversions = 2
→ winner declared
```

After guardrails:

```
exposures < 30
→ experiment remains RUNNING
```

Decision only happens after sufficient data.

---

## Notes

- This logic runs only inside the **winner detection phase**.
- No changes to routing, exposure tracking, or conversion logging.
- Guardrails simply delay the transition to DECIDED.
- Configuration values should remain constants for now.

---

## Result

The experiment lifecycle becomes:

RUNNING  
→ DATA ACCUMULATION  
→ GUARDRAIL CHECK  
→ DECISION  
→ DECIDED  
→ ENFORCED ROUTING

This prevents false winners while keeping the system lightweight.
