# Implementation Summary

## Section 1 — New API endpoints

### `functions/api/ab.js` (NEW — flat query-param style)

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/api/ab?alias=<alias>` | Returns `{alias, variants, updatedAt}` or 404 `{error:"no_ab_config"}` |
| PUT | `/api/ab` | Body: `{alias, variants}` — creates/replaces A/B config |
| DELETE | `/api/ab?alias=<alias>` | Removes A/B config for alias |

Stricter validation than the legacy path-param API (`api/ab/[alias].js`):
- `alias` must exist as `alias:<alias>` in `ALIAS_REGISTRY`
- each variant `slug` must exist in `LINKHUB_SLUGS`
- delegates structural validation (count, format, weight sum) to `validateABConfig()`

The legacy `api/ab/[alias].js` is **not modified** — both APIs coexist.

### `functions/api/ab-test.js` (NEW — diagnostics endpoint)

`GET /api/ab-test?alias=<alias>` — simulates one routing decision, returns:
```json
{ "alias": "ab26", "canonical_slug": "cd26-igbio", "final_slug": "cd26-yt", "variant": "B", "bucket": 73 }
```

### `functions/api/admin/aliases.js` (NEW — alias listing)

`GET /api/admin/aliases` — lists all `alias:*` keys from `ALIAS_REGISTRY`, sorted
alphabetically. Used by the admin panel to populate the A/B alias `<select>`.

## Section 2 — How the panel writes KV config

1. Operator opens the **Routing** tab → `loadAbAliases()` fetches `/api/admin/aliases` and populates the alias `<select>`.
2. Operator selects an alias and clicks **Load** → GET `/api/ab?alias=<alias>` returns existing config (or 404 → blank variant rows shown).
3. Operator configures variant slugs (from `<select>` populated via `slugCache`) and integer weights.
4. Operator clicks **Save Config** → client validates weight total = 100; PUT `/api/ab` body: `{alias, variants}`.
5. Server-side: validates alias exists in `ALIAS_REGISTRY`, each slug exists in `LINKHUB_SLUGS`, delegates structural check to `validateABConfig()`, writes `ALIAS_REGISTRY["ab_config:<alias>"]` and invalidates in-memory KV cache (`cacheDelete("ab_cfg:<alias>")`).

---

## Section 3 — How variant letters are assigned

Variant letters are derived deterministically from the **index** of the selected slug in the `variants` array:

```
variants[0] → A
variants[1] → B
variants[2] → C
…
```

Formula used in both `[[path]].js` and `ab-test.js`:
```js
const variantIdx    = abConfig.variants.findIndex(v => v.slug === finalSlug);
const variantLetter = variantIdx >= 0 ? String.fromCharCode(65 + variantIdx) : null;
```

The letter is appended as `utm_variant=A` (or B/C…) to `defaultUtms` in `[[path]].js` when A/B routing is active. This flows into every hub link URL alongside the existing UTM parameters.

Example final URL:
```
https://niluferormanli.com/?utm_source=instagram&utm_medium=bio&utm_campaign=cd26-test&utm_content=primary_official&utm_variant=A
```

## Section 4 — Diagnostics endpoint logic

`GET /api/ab-test?alias=<alias>`:

1. Reads compiled route from `ROUTE_TABLE["route:<alias>"]` → `canonical_slug`
2. Loads A/B config via `loadABConfig(alias, env)` (uses shared ab-router.js, with in-memory cache)
3. Generates a fresh `crypto.randomUUID()` as `requestId`
4. Calls `selectABVariant(abConfig, requestId)` → `final_slug`
5. Finds `variantIdx` of `final_slug` in `abConfig.variants` → letter (A/B/C…)
6. Replicates the internal bucket formula: `parseInt(hex.slice(-8), 16) % 100`
7. Returns all fields including `bucket` for transparency

The admin panel card in the **Diagnostics** tab (`abd-alias-input`, `btn-abd-run`) calls this endpoint and renders the JSON result in a `<pre>` block.
