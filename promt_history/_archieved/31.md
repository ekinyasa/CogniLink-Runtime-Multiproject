# Implementation Summary

## Section A — Root cause of UTM preset inconsistency

`buildDefaultUtms(canonicalSlug)` works by extracting the **last dash-separated
suffix** of the slug name and doing a lookup in `CHANNEL_UTM`:

```js
const channelSuffix = canonicalSlug.slice(canonicalSlug.lastIndexOf("-") + 1);
return CHANNEL_UTM[channelSuffix] || {};
```

It reads **only from the slug name** — not from the preset field, not from stored
`defaults`, not from the alias. The admin panel's `PRESET_SUFFIX` appends a
channel token to every generated slug name (e.g. `campaign-name-spbio`), but
`CHANNEL_UTM` only had 5 entries: `igbio`, `igstory`, `yt`, `youtube`, `spotify`.

The seven missing tokens (`spbio`, `ttbio`, `ttstory`, `ttpaid`, `fbpost`, `meta`,
`google`) all returned `{}`, so only `utm_campaign` and `utm_content` were generated
— `utm_source` and `utm_medium` were silently missing.

**Why IG / YouTube worked:** their tokens (`igbio`, `igstory`, `yt`) were in
`CHANNEL_UTM` from the start.

**Secondary issue (Section C):** the slug record already stores `utm_source` and
`utm_medium` in `slug.defaults` (written from the selected UTM preset at create
time). `buildDefaultUtms()` never consulted this stored data — it always
re-derived from the slug name heuristic, which failed for new tokens.

## Section C — UTM derivation priority order (final)

```
1. slug.defaults  (stored at create time from selected UTM preset)  ← highest priority
2. CHANNEL_UTM[suffix]  (heuristic from slug name's last segment)
3. {}  (utm_campaign + utm_content only)                            ← lowest priority
```

Implementation in `functions/[[path]].js`:
```js
const slugUtms    = buildDefaultUtms(finalSlug);
const storedUtms  = (hubConfig?.defaults && typeof hubConfig.defaults === "object")
  ? hubConfig.defaults : {};
const defaultUtms = Object.assign({}, slugUtms, storedUtms);
```

`Object.assign` order puts `storedUtms` last so it wins over `slugUtms`. For old
slug records without a `defaults` field, `storedUtms` is `{}` and suffix derivation
is the effective source.

## Section E — Constant-time token comparison

`functions/_shared/auth.js` — `verifyToken()` changed from `===` to
`crypto.subtle.timingSafeEqual` (Cloudflare Workers synchronous extension):

```diff
- return token === env.ADMIN_TOKEN;
+ const enc = new TextEncoder();
+ const a   = enc.encode(token);
+ const b   = enc.encode(env.ADMIN_TOKEN);
+ if (a.byteLength !== b.byteLength) return false;
+ return crypto.subtle.timingSafeEqual(a, b);
```

- `crypto.subtle.timingSafeEqual(a, b)` is a CF-Workers-specific extension to
  the Web Crypto API. It is **synchronous** (returns `boolean`, not a Promise),
  so no callers needed to be changed to `async/await`.
- Length is checked before calling `timingSafeEqual` because the function throws
  on unequal-length inputs (it does not return `false`). An attacker who submits
  a wrong-length token still gets a constant-time-style response since the
  length check is O(1) and the response timing is dominated by network jitter.
- Auth flow, bearer token format, `env.ADMIN_TOKEN`, localStorage behavior —
  all unchanged.
