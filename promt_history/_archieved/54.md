

# Prompt 54 — Bandit Stabilization, Cron Ownership, and Safe Rebalancing

Context

We are evolving the Campaign OS experiment system toward a single, deterministic, low‑cost learning mechanism that works safely under viral traffic conditions.

The system runs on Cloudflare Workers + KV and must remain extremely lightweight. Our goal is not academic A/B testing but continuous traffic allocation toward the best‑performing variant while preserving exploration.

This prompt cleans up the experiment learning architecture and stabilizes the bandit mechanism.

Key Principles

1. Edge‑safe
2. KV‑only
3. Deterministic routing
4. Minimal compute
5. Safe under sudden traffic spikes
6. No competing learning systems

Important: After this prompt there must be only ONE system that updates experiment weights.


SECTION 1 — Cron Becomes the Only Learning Mechanism

The experiment learning system must be owned exclusively by the scheduled cron worker.

Cron job:

functions/cron/bandit-update.js

Responsibilities:

• read experiment analytics
• compute variant performance
• rebalance variant weights
• persist new weights

Manual bandit endpoints must NOT modify weights anymore.

If a manual endpoint exists (for example:

/api/experiments/:alias/bandit

)

it must be converted into a "manual trigger" that simply calls the same rebalance function used by cron.

Example behavior:

POST /api/experiments/:alias/rebalance

→ triggers the same rebalance logic used by cron
→ does not contain its own bandit logic

This ensures there is only ONE algorithm updating weights.


SECTION 2 — Weight Movement Must Be Limited (Delta Guard)

Weights must not jump aggressively between updates.

We introduce a delta limiter:

max_delta = 10

Meaning a variant weight may only change by ±10 per rebalance cycle.

Example:

old weight: 50
computed target weight: 80

new weight:

min(old + max_delta, target)

→ 60

Likewise:

old weight: 50
target weight: 20

new weight:

max(old - max_delta, target)

→ 40

This prevents traffic shock when conversion data changes quickly.


SECTION 3 — Exploration Floor

No variant should ever receive zero traffic.

Minimum variant weight:

MIN_WEIGHT = 10

After computing target weights, clamp them so that:

variant.weight >= MIN_WEIGHT

Then normalize the total so the sum remains 100.

This guarantees that new or recovering variants still receive data.


SECTION 4 — Rebalance Algorithm

The rebalance process should follow this order:

1. Collect exposures and conversions per variant
2. Compute conversion rate

score = conversions / exposures

3. Normalize scores

normalized_weight = score / sum(scores)

4. Convert to percentage weights

5. Clamp to minimum weight

6. Apply delta guard (max_delta)

7. Normalize again to ensure sum = 100

8. Persist updated weights

This produces smooth traffic shifts instead of abrupt reallocations.


SECTION 5 — Sample Size Guard

The bandit update must only run if the experiment has enough data.

Minimum thresholds:

experiment_exposures >= 200
variant_exposures >= 50

If thresholds are not met:

→ skip rebalance

This avoids noise‑driven allocations.


SECTION 6 — KV Safety

Weight updates must be atomic.

When writing updated experiment weights:

• read experiment record
• update weights
• write back in a single KV put

No partial updates.

Do not split variant state across multiple keys.


SECTION 7 — Logging

Each rebalance run should log:

experiment alias
variant exposures
variant conversions
old weights
new weights

Logs should remain lightweight (console only).


SECTION 8 — System Result

After Prompt 54 the experiment system architecture becomes:

Edge Router
→ deterministic variant selection
→ exposure tracking
→ conversion verification
→ cron bandit learning

Cron performs periodic learning updates.

Routing remains deterministic and extremely fast.

No request‑time bandit computation occurs.


SECTION 9 — Non‑Goals

This system intentionally does NOT implement:

• Bayesian Thompson sampling
• statistical significance testing
• request‑time bandit evaluation

Those approaches increase complexity and compute cost.

Campaign OS prioritizes:

• speed
• cost efficiency
• operational simplicity


SECTION 10 — Expected Outcome

After implementation:

• experiments learn automatically
• traffic flows toward better variants
• exploration is preserved
• system remains stable during viral spikes
• cost remains near‑zero

## Implementation Summary

### Architecture change (Section 1)

`rebalanceExperiment(env, alias)` in `functions/cron/bandit-update.js` is now the **single algorithm** that modifies variant weights. No other code path writes to `variant.weight`. `POST /api/experiment/bandit-update` is a thin auth wrapper that calls this function — it owns no bandit logic of its own.

---

### Files Modified

#### `functions/cron/bandit-update.js` — full rewrite

**Constants**
- `MIN_WEIGHT = 10` (exploration floor, Section 3)
- `MAX_DELTA = 10` (delta guard, Section 2)
- `MIN_VARIANT_EXPOSURES = 50`, `MIN_TOTAL_EXPOSURES = 200` (sample size guard, Section 5)
- Removed `MAX_WEIGHT = 80` (Prompt 53) — superseded by the delta guard

**`normalizeToSum100(weights)`** — helper
- If sum < 100: adds deficit to the largest variant
- If sum > 100: greedily subtracts 1 at a time from the heaviest variant with room above MIN_WEIGHT until surplus is eliminated

**`computeRebalancedWeights(variants, counters)`** — replaces `computeSoftBanditWeights`
- Steps 2–7 from Section 4 in exact order:
  1. Per-variant exposure check → `null` if any variant < 50 (whole experiment skipped)
  2. `score[i] = conversions[i] / exposures[i]` (zero-conversions → equal distribution)
  3. `normalized[i] = score[i] / sum(scores)`
  4. `weights[i] = round(normalized[i] × 100)`
  5. `weights[i] = max(weights[i], MIN_WEIGHT)` — exploration floor
  6. `weights[i] = clamp(weights[i], old[i] − MAX_DELTA, old[i] + MAX_DELTA)` — delta guard
  7. `normalizeToSum100(weights)` — final renormalization

**`rebalanceExperiment(env, alias)`** — NEW named export
- Single source of truth for weight updates
- Returns a structured result object:
  - `{ ok: false, reason }` — config missing or KV error
  - `{ ok: true, action: "skipped", reason, state, ... }` — guard not met; no write
  - `{ ok: true, action: "no_change", state, variants }` — computed == current; no write
  - `{ ok: true, action: "updated", state, variants }` — weights written to KV
- `variants[i]` shape: `{ slug, exposures, conversions, old_weight, new_weight }`
- Section 7 log includes all fields: variant exposures, conversions, old weights, new weights:
  ```
  BANDIT_UPDATE {"experiment":"abrand45","variants":[{"slug":"ab-rand-45-ttbio","exposures":312,"conversions":47,"old_weight":50,"new_weight":60},{"slug":"ab-rand-45-igbio","exposures":288,"conversions":28,"old_weight":50,"new_weight":40}],"old_weights":{...},"new_weights":{...}}
  ```
- Single KV put for atomicity (Section 6): read config → update weights → `ALIAS_REGISTRY.put` → `cacheDelete`
- Cache invalidated after write so router picks up new weights within ≤ 60 s

**`runBanditUpdate(env)`** — updated to call `rebalanceExperiment`
- No longer calls the private `tryUpdateExperiment` — directly calls `rebalanceExperiment(env, alias)` for each key
- Counts only `action === "updated"` as an update in the summary log

#### `functions/api/experiment/bandit-update.js` — refactored

**Removed:**
- `import { computeBanditWeights, EXPLORATION_FLOOR_PCT } from "../../_shared/bandit.js"` (Thompson sampling)
- `import { getExpCounters, NUM_SHARDS }` (now in cron module)
- `import { getExpState }` (now in cron module)
- `import { cacheDelete }` (now in cron module)
- All Beta posterior / Thompson sampling computation
- Auto-archive logic (`INACTIVITY_DAYS`, inactivity check)
- `dry_run` support

**Added:**
- `import { rebalanceExperiment } from "../../cron/bandit-update.js"`
- The `onRequestPost` handler is now ~30 lines: auth → parse body → `rebalanceExperiment` → map result to HTTP response

**Response shape change:**
- Old: `{ ok, alias, state, weights: [{slug, weight, alpha, beta}] }`
- New: `{ ok, alias, action, state, variants: [{slug, exposures, conversions, old_weight, new_weight}] }`

### Delta guard — worked example (Section 2)

```
Variant A: old_weight=50, target=80  → guarded = min(50+10, 80) = 60
Variant B: old_weight=50, target=20  → guarded = max(50-10, 20) = 40
Sum = 100 ✓  No normalization needed.
```

Next cycle (if trend continues):
```
Variant A: old_weight=60, target=80  → guarded = 70
Variant B: old_weight=40, target=20  → guarded = 30
Sum = 100 ✓  Reaches target [80,20] in 3 cycles (30 min at 10-min cron).
```

---

### Request-path latency impact

**Zero.** `rebalanceExperiment` is never called from `[[path]].js` or `experiment-router.js`. The router reads only `variant.weight` from KV (via the in-memory cache) — it never runs any learning computation. New weights become visible to the router passively when the cache TTL expires (≤ 60 s).
