# Prompt 27 — Admin Panel: Campaign Persistence + A/B Config UI

Prompt 26 test results revealed two issues to fix.

---

## Issue 1 — Campaign selection not remembered

After a deploy (or page reload), the slug creation form always resets
to the most recently created campaign instead of the campaign the operator
was last working with.

The fix: persist the last selected campaign in localStorage so the form
restores the correct selection on every page load.

---

## Issue 2 — No A/B Config UI

Prompt 26 implemented the A/B routing backend (ab-router.js, /api/ab/:alias).
However there is no admin panel UI to manage A/B configs.
Operators currently must make raw API calls using browser devtools.

The fix: add an "A/B Routing" card inside the existing Routing tab.

The card must allow:

- Load current A/B config for any alias
- Edit variant slugs and weights
- Save config (PUT /api/ab/:alias)
- Delete config (DELETE /api/ab/:alias)
- Live weight total so operator knows when weights sum to 100

---

## Constraints

- Do not add a new tab — place A/B config inside the existing Routing tab
- Use the same apiFetch / show / hide / esc helpers as the rest of the panel
- Store localStorage key under _sp_last_campaign
- Weight total indicator must turn green when total = 100, red otherwise

---

## Expected Result

After Prompt 27:

- Slug form always restores the last used campaign on reload
- Operator can create, view, edit and delete A/B routing configs from the panel
- No raw API calls required to manage experiments

## Fix 1 — Campaign persistence (Issue 27-1)

### Root cause

`populateCampaignSelect()` always selected `byRecency[0].name` — the most recently
created campaign — regardless of the operator's prior selection.
After any page reload (including post-deploy), the form defaulted back to this campaign.

### Fix

**`populateCampaignSelect()`** — read `localStorage["_sp_last_campaign"]` before
falling back to the recency-sorted default:

```js
var stored = "";
try { stored = localStorage.getItem("_sp_last_campaign") || ""; } catch (_e) {}
var validStored = stored && active.some(function (c) { return c.name === stored; });
var defaultCampaign = validStored ? stored : byRecency[0].name;
```

The stored name is validated against the current active campaign list so stale
or archived campaigns do not produce a broken selection.

**`elCampaignSelect.addEventListener("change", ...)`** — persist on every real selection:

```js
try { localStorage.setItem("_sp_last_campaign", elCampaignSelect.value); } catch (_e) {}
```

Only written when value is not `__new__` (the "create new campaign" synthetic option).

# Auth Regression Analysis (Prompt 28 — added retroactively)

After deploying Prompt 27, operators reported that all admin API calls returned 401 —
the Authorization header was missing from requests.

## Root cause

The token localStorage key was `"_sp_tok"` in code, but the operator's browser had the
token stored under `"admin_token"` (the canonical key from earlier versions).

The Prompt 23 v4 admin panel rewrite introduced `"_sp_tok"` as the storage key (likely
to avoid the word "admin" appearing in any user-visible or browser-visible surface).
Sessions that had already saved a token under `"_sp_tok"` continued to work. Sessions in
a fresh browser, incognito tab, or after clearing storage — or sessions that originated
before Prompt 23 and still held `"admin_token"` — found the in-memory `token` variable
was empty at boot, causing `apiFetch` to send `Authorization: Bearer ` (empty token),
which `verifyToken()` correctly rejects.

**Why it surfaced after Prompt 27:** Prompt 27 triggered a fresh Pages deploy. Operators
who opened the panel in a new browser session (or cleared storage between deploys) could
not authenticate. Operators in a running session still had `_sp_tok` in memory and were
unaffected — which is why the regression was intermittent and deploy-correlated.

**Prompt 27 itself did not cause the regression** — it was latent since Prompt 23.

## Fix applied in Prompt 28

Changed key name back to `"admin_token"` (canonical). Added a `TOKEN_KEY` constant
so any future rename is a single-line change with a clear comment warning against it.

## Security review of admin auth model

### Current design

```
Browser → localStorage["admin_token"] → apiFetch → Authorization: Bearer <token>
                                                  ↓
                                          verifyToken(request, env)
                                          token === env.ADMIN_TOKEN  (string equality)
```

### Strengths

- **No session cookies** — immune to CSRF attacks by design.
- **HTTPS in production** (Cloudflare Pages) — token is never transmitted in plaintext.
- **Stateless** — no session server, no token DB; revocation = change env var + redeploy.
- **Gate on 401** — panel auto-clears token and returns to login on any 401 response.
- **XSS defence** — all user-supplied values go through `esc()` before being written to DOM.

### Weaknesses

1. **Non-constant-time comparison** — `token === env.ADMIN_TOKEN` is not timing-safe.
   In theory, a remote attacker could use response timing to brute-force the token
   character by character. In practice, Workers network jitter makes this negligible,
   but `crypto.subtle.timingSafeEqual()` is the correct pattern for Workers:

   ```js
   // verifyToken — constant-time version (Worker-side only)
   function timingSafeEqual(a, b) {
     const ta = new TextEncoder().encode(a);
     const tb = new TextEncoder().encode(b);
     if (ta.length !== tb.length) return false;
     return crypto.subtle.timingSafeEqual(ta, tb);  // sync in Workers
   }
   ```

2. **Token in localStorage** — any XSS in the panel page can read `admin_token`.
   Mitigation already in place: `esc()` sanitises all dynamic content. Risk is low.

3. **No token expiry** — a leaked token is valid forever until `ADMIN_TOKEN` is rotated
   (which requires a Cloudflare dashboard change + redeploy).

4. **Single shared secret** — all operators share the same token. No per-operator audit
   trail. Acceptable for a single-operator studio tool.

### Recommendation

For this architecture (Cloudflare Workers + static Pages + bearer token), the current
model is appropriate. Suggested hardening priority:

1. *(Low effort, high value)* Switch `verifyToken()` to `crypto.subtle.timingSafeEqual()`
   to eliminate timing-oracle risk.
2. *(Low effort)* Keep `TOKEN_KEY = "admin_token"` constant — never rename it again.
3. *(Optional)* Add `SameSite=Strict` + `HttpOnly` session cookie as a second factor
   if the panel is ever exposed to a wider team. For now, bearer token is sufficient.

# GPT Evaluation — Prompt 27 Review

Prompt 27 is directionally correct and solves two real operator pain points without touching the routing core.

## What looks good

### 1. Campaign persistence fix is correct in principle
Using `localStorage` for the last active campaign is the right level of persistence for this problem.

Good aspects:
- no KV or backend complexity added
- stale value is validated against active campaigns
- fallback to recency still exists

This is a pragmatic UI fix.

### 2. A/B Config UI belongs in the Routing tab
This is the right placement.
A/B routing is a routing concern, not a campaign-content concern.

Good aspects:
- no new tab added
- uses existing admin helpers
- keeps the experiment workflow inside the routing surface

### 3. Weight total indicator is a good operator safeguard
The green/red total check is simple and useful.
It reduces trivial config mistakes before save.

### 4. Single-file implementation is acceptable here
Because this is admin UI glue and not engine logic, keeping it in `admin-renderer.js` is acceptable for now.

---

## Weak / risky points to watch

### 1. localStorage key is global, not project-scoped
`_sp_last_campaign` is fine for now, but it is global to the panel in this browser.
That is acceptable in the current single-brand setup.
It would become weak only if the panel later serves multiple brands or environments.

No action needed now.

### 2. A/B UI allows invalid slug names until save
This is not wrong, but it means validation is mostly deferred to the API.
That is acceptable, but during testing we should confirm errors surface clearly and do not leave the editor in a confusing state.

### 3. No obvious mention of alias existence validation before load
The summary says the UI can load config for any alias.
We should verify what happens when the alias does not exist at all.
Best case: clear error.
Worst case: ambiguous “no config” state.

This is the main thing to watch during testing.

### 4. Delete flow may be too destructive if there is no confirmation
The summary does not mention a confirmation step before DELETE.
That is not automatically wrong, but it is risky UX.
If delete happens instantly with one click, operator mistakes become easier.

Not a blocker, but worth checking.

---

## Verdict before testing

Prompt 27 looks reasonable and low-risk.
No obvious architectural mistake appears in the summary.

The main unknowns are runtime UX details:
- does campaign persistence actually restore the right campaign after reload?
- does A/B config load/save/delete behave clearly?
- do validation and error states stay understandable?

So the correct status is:

`READY FOR RUNTIME TESTING`
