# Prompt 42 — Experiment Diagnostics & Analytics UI

Goal: introduce the first **observability layer** for experiments inside Campaign OS.

Up to this point the system can:

- route traffic
- run A/B experiments
- record conversions

However there is **no fast way to observe experiment health** during runtime.

Prompt 42 adds a lightweight analytics UI focused on **diagnostics**, not statistical analysis.

# Exposure Counters

To support diagnostics we introduce **experiment exposure counters**.

Each time a variant is served the system increments a KV counter.

### Increment Point

The exposure counter must be incremented immediately after the experiment
variant is decided but **before the redirect occurs**.

Logical flow:

experiment decision
↓
increment exposure counter
↓
redirect to variant destination

This guarantees that every routed request counts as an exposure.

KV schema:

```
exp:exposure:<experiment>:<variant>
```

Example:

```
exp:exposure:ab-test-1:igbio
exp:exposure:ab-test-1:spbio
```

Optional total counter:

```
exp:exposure:ab-test-1:total
```

### Namespace

Exposure counters should live in the same KV namespace currently used
for experiment metadata unless a dedicated analytics namespace already
exists.

Keys are intentionally simple and append‑only because they are used only
for diagnostics.

These counters allow the admin panel to show:

- traffic distribution
- exposure totals
- basic experiment health

This layer is intentionally **approximate**.

KV eventual consistency is acceptable because:

- diagnostics only
- not used for final statistics

# Evaluation

Prompt 42 introduces **observability without altering routing logic**.

Important design decisions:

- counters stored in KV
- diagnostics only
- no statistical engine
- no routing side effects

This keeps the experimentation core deterministic while improving operator visibility.

## What Prompt 42 added

Single file changed: **`functions/admin/experiments.js`**

### Layer 2.5 — Traffic Distribution card

New diagnostics card inserted between the Variant Performance table and the Bar Chart. Shows exposure share per variant as a proportional bar visualization, alongside the configured weight target.

**Columns:** Variant slug | bar | Actual share % | Target weight %

**Imbalance detection:** if |actualPct − expectedPct| > 10 pp for any variant → row highlighted amber + warning strip shown.

#### `renderDistribution(variants)` summary

- Hidden when `totalExp === 0` (experiment has no traffic yet)
- For each variant: `actualPct = exposures / totalExp * 100` (1 dp)
- `expectedPct = v.weight` — already in the `/api/experiments` response; no extra KV read
- `isImbalance = |actualPct − expectedPct| > 10`
- Imbalance row: amber bar + amber pct via `.dist-row.dist-imbalance`
- Warning message: `⚠ Traffic imbalance — actual distribution differs from configured weights by >10 pp`

#### CSS added

`.dist-row`, `.dist-label`, `.dist-bar-wrap`, `.dist-bar`, `.dist-pct`, `.dist-expected`, `.dist-row.dist-imbalance`, `.dist-warning` (dark-mode variant included)

## No backend changes

All data needed (`exposures`, `weight`) was already present in the `/api/experiments` response. No new endpoints, no KV schema changes, no routing modifications.

## Design decisions

- **Separate card from performance table**: distribution is a distinct diagnostic signal; mixing it into the multi-column table would reduce scannability
- **10 pp imbalance threshold**: matches `WINNER_THRESHOLD` — consistent "meaningful difference" bar for this system
- **Hidden when no data**: zero-exposure experiments keep the card hidden rather than showing an empty or misleading state
- **`v.weight` as target**: the configured split weight is already returned by the API so the UI computes expected vs actual entirely client-side


Important note: If experiment.status === decided
distribution may diverge from configured weights
because routing switches to winner mode. (not imbalance bug) Winner state may override configured weights.
