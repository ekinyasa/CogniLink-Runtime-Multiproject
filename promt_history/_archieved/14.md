Campaign OS – Prompt 14.md

Goal

We already implemented a working smoke test system
(Diagnostics tab + /api/admin/smoke-test endpoint).

Now we want to improve the testing layer to achieve two goals:

1) Ensure the system is reliably alive
2) Ensure the system behaves correctly with real data

Important definitions:

Smoke test  = "system alive"
Manual test = "system correct"

Testing improvements must NOT refactor the router or campaign logic.

Only extend the testing layer.

--------------------------------------------------

Testing Philosophy

Campaign OS testing must follow a layered model:

Layer 1 — Smoke Test
Verifies infrastructure health and routing behaviour.

Layer 2 — Consistency Probe
Verifies telemetry + analytics pipeline integrity without mutating data.

Layer 3 — Manual Deterministic Test
Validates real data aggregation behaviour.

--------------------------------------------------

PART 1 — Harden Smoke Test Reliability

Update runSmokeTests() in:

/functions/_shared/test-runner.js

The smoke test must confirm the following subsystems:

Router
Modifier routing
KV registry
Telemetry emission
Analytics ingestion

--------------------------------------------------

1. Router Resolution Verification

The router must prove it resolved a campaign route.

Acceptable signals:

• HTTP status 200 or 302
• Response is NOT the static fallback page
• Redirect target differs from request URL

Router validation rule:

status = 200 OR 302
AND response is not fallback page

This confirms that alias routing works.

--------------------------------------------------

2. Modifier Routing Verification

Smoke tests must confirm modifier resolution without relying on analytics.

Test requests:

GET /nb
GET /nb/offer
GET /nb/vsl

Validation rules:

/nb/offer must resolve modifier "offer"
/nb/vsl must resolve modifier "vsl"

Signals may include:

• redirect target differences
• modifier routing metadata
• telemetry payload values

Do NOT rely on Analytics Engine for this verification.

--------------------------------------------------

3. KV Registry Health Check

Smoke test must confirm that critical KV bindings are readable.

Verify read access for:

ALIAS_REGISTRY
ROUTE_TABLE
HUB_CONFIG

Implementation rule:

Attempt a read operation using env bindings.

Fail if:

• binding does not exist
• read throws an error

Read-only operations only.

--------------------------------------------------

4. Telemetry Emission Verification

Telemetry is considered PASS if router requests complete successfully.

Reason:

Telemetry write-through verification cannot be guaranteed inside the same request cycle.

Therefore:

Successful router + modifier resolution
→ implies telemetry emission triggered.

Do NOT attempt write-through validation.

--------------------------------------------------

5. Analytics Engine Verification (Retry Strategy)

Analytics Engine ingestion is eventually consistent.

Replace fixed wait with retry loop.

Retry strategy:

wait 1s
query events

wait 2s
query events

wait 4s
query events

wait 8s
query events

Stop early if events are found.

Maximum verification window: ~15 seconds.

Verification rule:

Recent alias_click events must exist within last 5 minutes.

Delta-Based Verification

After test:

Compute:

Validation rules:

### PART 1 ✅ — Smoke Test Hardening (`functions/_shared/test-runner.js`)

**Router Resolution (Layer 1A):** `200 OR 302` + static fallback algılama
- `body.length < 500 || (!body.includes("hub-") && !body.includes("<!DOCTYPE"))` → fallback tespiti
- Fallback durumunda `{ ok: false, fallback: true }` dönüyor

**KV Registry Health Check (Layer 1B) — YENİ:**
```js
const KV_BINDINGS = [
  { label: "ALIAS_REGISTRY", envKey: "ALIAS_REGISTRY"  },
  { label: "ROUTE_TABLE",    envKey: "ROUTE_TABLE"     },
  { label: "HUB_CONFIG",     envKey: "LINKHUB_CONFIG"  },
];
```
Her binding için `.list({ limit: 1 })` — değer okumaz, ucuz probe. Binding yoksa veya read hata verirse FAIL.

**Telemetry (Layer 1C):** Değişmedi — router istekleri başarılıysa "pass" (write-through single cycle içinde doğrulanamaz)

**Analytics — Retry Loop (Layer 1D) — YENİ:**
```
Fixed 400ms wait → Exponential retry: 1s → 2s → 4s → 8s (≈15s max)
```
Event bulunur bulunmaz erken çıkış. AE credentials yoksa warnings'e not düşer, testi kesmez.

**Return shape (6 alan, eski 4'tü):**
```json
{ ok, router, modifier, kv, telemetry, analytics, consistency, duration_ms, warnings }
```
