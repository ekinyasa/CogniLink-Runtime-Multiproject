# Prompt 20 — Campaign OS Stabilization Pass

## Context

Campaign OS is a serverless campaign routing and attribution system running on:

- Cloudflare Pages Functions
- Cloudflare KV
- Cloudflare Analytics Engine

The system has already implemented:

- alias router
- campaign registry
- modifier routing
- hub renderer
- analytics ingestion
- diagnostics panel
- system tests
- manual validation
- background tests

Prompt 19 introduced improvements but testing revealed several **critical operational problems**.

This prompt is **NOT for new features**.

This is a **stabilization pass**.

Goal:

Make Campaign OS reliable for real production use managing campaigns for a single high‑activity personal brand.

Production context:

Brand: Nilüfer Ormanlı
Traffic sources include:

- Instagram bio
- Instagram story
- YouTube
- future: TikTok / Spotify / Apple Music

Campaign OS must function as a **reliable marketing operations console**.

Primary requirements:

1. Routing must always work without manual intervention
2. Campaign creation must be fast
3. Analytics must remain trustworthy
4. Diagnostics must clearly expose failures

No system behavior should require operators to remember hidden maintenance steps.

---

# 1 — Remove Manual Routing Activation Requirement

## Problem

Currently public routing only works after running:

Compile Routes

This creates a dangerous production workflow.

Example failure case:

Operator creates campaign → shares link → alias returns 404 because compile was forgotten.

Routing must activate automatically.

## Required change

When a campaign, slug, or alias is created or modified:

compileRoutes() must run automatically.

Compile button in admin panel should remain but function only as:

"Force rebuild ROUTE_TABLE"

not as required step for activation.

## Implementation requirement

Trigger compileRoutes() after:

- campaign creation
- slug creation
- alias creation
- campaign update affecting routing

Compile must remain deterministic.

---

# 2 — Fix Manual Validation Fixture Routing

## Observed failure

Manual validation expected sequence:

/alias
/alias
/alias/offer
/alias/vsl

Observed behavior:

Only /alias events recorded.

Modifier routes were not resolving.

## Root cause

Fixture campaigns created during tests do not generate modifier routes.

## Required fix

Fixture campaign must generate:

alias
alias/offer
alias/vsl

routes exactly like real campaigns.

Manual validation must then execute the correct sequence.

---

# 3 — Improve Analytics Retry Logic

Cloudflare Analytics Engine ingestion delay may reach ~30‑60 seconds.

Current retry window is too short.

Update retry strategy:

retry after 1s
retry after 2s
retry after 4s
retry after 8s
retry after 16s
retry after 32s

Total verification window ~63 seconds.

Manual validation should only fail after exhausting retries.

---

# 4 — Fix Alias Hub vs Slug Hub Rendering

## Observed behavior

Slug hub page:

/c/<slug>

Correctly renders custom links.

Alias hub page:

/<alias>

Ignores slug overrides and only uses campaign defaults.

## Required behavior

Alias hub must resolve slug first.

Rendering priority must be:

slug override
→ campaign default

Alias hub must produce identical output to slug hub.

---

# 5 — Repair Background Self Test Diagnostics

Current background test simply reports:

"Background test failed"

with no diagnostic reason.

This makes the test useless operationally.

## Required change

Return structured result:

{
 ok: false,
 stage: "analytics",
 reason: "AE timeout",
 duration_ms: 4231,
 timestamp: "...",
 fixture: {
  alias,
  campaign,
  slug
 }
}

Stages should include:

- router
- registry
- telemetry
- analytics

This allows operators to quickly identify failure location.

---

# 6 — Fix Slug Table Test Filter

Observed issue:

"Show test campaigns" filter hides all slug rows.

Cause:

slug table filtering does not correctly join campaign metadata.

Required fix:

Slug filtering should evaluate:

slug.startsWith("test-")

or equivalent canonical rule.

Filter must behave consistently across:

- campaign table
- alias table
- slug table
- recent events

---

# 7 — Add Router Status Panel

Operators currently cannot see router state.

Add simple router status block to admin diagnostics.

Example:

Router Status

Registry aliases: 12
Compiled routes: 12
Router active: YES
Last compile: 18:03:21

This prevents invisible routing problems.

---

# 8 — Admin Verify Route

Previous attempt assumed a page route:

/admin/verify/<alias>

This is unreliable with current admin structure.

Instead implement API endpoint:

/api/admin/verify

Usage:

/api/admin/verify?alias=<alias>

Behavior:

Render hub preview with diagnostic overlay.

Authorization must use ADMIN_TOKEN.

# 9 — Preserve Core Router Guarantees

All changes must maintain these invariants:

Alias resolution O(1)

resolveAlias may only read:

- ROUTE_TABLE
- Workers Cache

No runtime scanning of registry objects.

# Response — Prompt 20 Implementation

All 8 stabilization tasks completed.

## PART 1 — Auto-compile routes (DONE)

Added `compileRoutes()` fire-and-forget (`context.waitUntil`) after alias write in:

- `functions/api/campaign/index.js` — POST (new campaign with alias)
- `functions/api/slug/index.js` — POST (new slug with alias)
- `functions/api/slug/[slug].js` — PUT (alias set or cleared)
- `functions/api/campaign/[name].js` — PATCH (alias set or cleared)

Routing activates automatically. Compile button remains as force-rebuild.

## PART 2 — Fixture modifier routing (DONE)

`functions/_shared/fixture.js` `createFixture()` now also writes:

- `ROUTE_TABLE["route:{alias}@offer"] = slug`
- `ROUTE_TABLE["route:{alias}@vsl"] = slug`
- `LINKHUB_SLUGS[slug] = { slug, campaign, isActive, isTest, ... }`

`archiveFixture()` cleans up all three ROUTE_TABLE keys and the LINKHUB_SLUGS record.

Modifier routes are now explicit (no dependency on fallback logic). Hub config available for alias route rendering.

## PART 3 — AE retry window (NO CHANGE NEEDED)

Current `retry.js` uses `[1s, 2s, 4s, 8s, 16s, 32s, 32s]` = 95s total window.
This exceeds the 63s spec requirement. No change needed.

## PART 4 — Alias hub vs slug hub parity (DONE)

`functions/_shared/alias-router.js` `loadHubConfig()`: removed `ENABLE_LEGACY_HUB_FALLBACK` gate.

LINKHUB_SLUGS is now always read as fallback when HUB_CONFIG misses.
Slug records written via `/api/slug` now render correctly through alias routes.

## PART 5 — Background test diagnostics (DONE)

`functions/api/admin/background-test.js` `runBackgroundTest()` now tracks `stage` variable
(`telemetry`, `registry`, `router`, `analytics`, `complete`) and returns structured:

```json
{ "ok": false, "stage": "analytics", "reason": "AE timeout", "duration_ms": 4231, "timestamp": "...", "fixture": { "alias": "...", "campaign": "...", "slug": null } }
```

Failure results are also persisted to `LINKHUB_CONFIG["_bg_test_last"]` with stage info.

## PART 6 — Slug table test filter (DONE)

`functions/_shared/admin-renderer.js` `renderList()` `isTest` now also checks:

```js
(s.slug && s.slug.startsWith("test-"))
```

Filter works even when test campaign records are absent from the loaded campaigns array.

## PART 7 — Router Status Panel (DONE)

`functions/api/admin/compile-routes.js`:
- Added `GET` handler returning `{ aliases, routes, active, lastCompile }` from ALIAS_REGISTRY and ROUTE_TABLE live counts.
- After successful `POST` compile, persists `{ timestamp, routes, aliases }` to `LINKHUB_CONFIG["_last_compile"]`.

`functions/_shared/admin-renderer.js` Routing tab:
- Added Router Status card with live counts table (Registry aliases / Compiled routes / Router active / Last compile).
- Status loads on first tab open and on Refresh button click.
- Routing note updated: "Routing activates automatically when aliases are created."

## PART 8 — Admin Verify API endpoint (DONE)

Created `functions/api/admin/verify.js`:

- Route: `GET /api/admin/verify?alias=<alias>`
- Auth: `Authorization: Bearer <ADMIN_TOKEN>` (consistent with all admin APIs)
- Behavior: renders hub preview + link-validation overlay (✔/⚠/✖ badges), or archived diagnostic page if alias not in ROUTE_TABLE.

Old page route `/admin/verify/[alias].js` retained for backwards compatibility.

# GPT Değerlendirme — Prompt 20 Implementation Review

Prompt 20 çıktısı incelendiğinde Claude'un yanıtı genel olarak hedeflenen **stabilization pass** kapsamıyla uyumludur. Kod tarafında yeni platform soyutlamaları eklenmemiş, mevcut mimari korunarak operasyonel sorunlar ele alınmıştır.

Bu aşamada değerlendirme şu şekilde yapılır:

## Kabul Edilen Değişiklikler

1. **Auto‑compile routing**

Alias / campaign / slug yazımı sonrası `compileRoutes()` tetiklenmesi doğru yaklaşımdır.
Bu değişiklik Campaign OS için kritik olan şu problemi çözer:

"kampanya oluşturuldu ama route compile edilmediği için link çalışmıyor".

Operatör hatasına bağlı kırılganlık ortadan kaldırılmıştır.

2. **Fixture modifier routing**

Test fixture'larının artık:

- alias
- alias/offer
- alias/vsl

route'larını explicit olarak yazması doğru yaklaşımdır.

Bu değişiklik manual validation testinin deterministik çalışması için gereklidir.

3. **Alias hub → slug hub parity düzeltmesi**

Alias router'ın `LINKHUB_SLUGS` fallback kullanması doğru çözümdür.

Production davranışı şu olmalıdır:

alias linki → slug konfigürasyonunu aynen render eder.

Creator tarafında dağıtılan linkler alias olduğu için bu parity kritik bir gerekliliktir.

4. **Background test diagnostics**

Stage bazlı hata raporu eklenmesi doğru yöndedir.

En önemli kazanım:

```
router
registry
telemetry
analytics
```

katmanlarından hangisinin kırıldığının operatör tarafından görülebilmesidir.

5. **Slug test filter düzeltmesi**

`slug.startsWith("test-")` fallback kontrolü doğru yaklaşımdır.

Slug tablosu artık campaign metadata eksik olsa bile test filtreleriyle çalışabilir.

6. **Router status panel**

Admin arayüzünde router durumunun görünür olması operasyonel olarak önemlidir.

Operatör artık şu bilgileri görebilir:

- registry alias sayısı
- compiled route sayısı
- router aktif mi
- son compile zamanı

7. **Admin verify API**

`/api/admin/verify` endpoint'i önceki `/admin/verify/<alias>` yaklaşımından daha güvenilir bir çözüm.

Admin işlemlerinin API üzerinden yapılması mimari olarak daha doğru.
