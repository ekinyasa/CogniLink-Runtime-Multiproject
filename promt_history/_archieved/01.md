Campaign OS — Alias Routing Layer: Implementation Design
1. Architectural Position
The alias routing layer is purely additive. Every existing file (c/[slug].js, ig.js, youtube.js, spotify.js, hub-renderer.js, links.js, analytics.js, all existing API routes) is untouched. The new layer sits in front of the canonical rendering pipeline and resolves /<alias> and /<alias>/<modifier> into canonical slugs before handing off to the same resolveLinks() + renderHub() path that /c/:slug already uses.

The canonical slug becomes the only identity passed into rendering and analytics. Neither the alias nor the modifier crosses that boundary.

  _shared/
    alias-router.js               # NEW — shared resolution pipeline
    analytics.js                  # existing — unchanged

Pages Functions route precedence
Cloudflare Pages Functions resolve routes from most-specific to least-specific. The dynamic [alias].js and [alias]/[modifier].js files only receive requests that no more-specific route handles first. This means all existing routes (/ig, /youtube, /spotify, /nilufer, /api/**, /c/**) are unaffected and continue serving normally — no changes needed to existing handlers.

3. KV Namespaces
Two new KV namespaces are added. The three existing namespaces are untouched.

ALIAS_REGISTRY
Stores alias bindings and override exceptions.

Key pattern	Value
alias:<alias>	JSON: { campaign_id, created_at, updated_at, routing_revision }
alias_override:<alias>@<modifier>	JSON: { canonical_slug, created_at, reason }
The routing_revision is a monotonic integer used as an optimistic lock for safe reassignment. It is read before any write and passed back as a precondition on PUT.

CAMPAIGN_REGISTRY
Stores campaign routing definitions. Separate from the existing LINKHUB_CAMPAIGNS (which stores admin panel campaign lifecycle state). These are different concerns.

Key pattern	Value
campaign:<campaign_id>	JSON: see schema below
Campaign record schema:

{
  "campaign_id": "album-launch",
  "default_channel": "igbio",
  "channels": ["igbio", "igstory", "yt"],
  "modifier_map": {
    "ig":      "igbio",
    "insta":   "igbio",
    "yt":      "yt",
    "youtube": "yt"
  },
  "routing_revision": 1,
  "created_at": "2026-03-01T00:00:00.000Z",
  "updated_at": "2026-03-01T00:00:00.000Z"
}

modifier_map is the authoritative synonym table. The channel resolution step looks up the modifier here exclusively — never by iteration or prefix scan.

Existing namespaces
After the alias resolution pipeline produces a canonical slug, the handler reads from LINKHUB_SLUGS.get(canonical_slug) and LINKHUB_CONFIG.get("hub_config") exactly as /c/:slug does. No new keys or key formats are added to those namespaces.

4. alias-router.js — The Resolution Pipeline
This module exports a single function:

resolveAlias(alias, modifier, env)
  → Promise<{ ok: true, canonicalSlug, slugRecord, config }>
  | Promise<{ ok: false, status: 404 | 500, reason: string }>

The reason string maps directly to the observability taxonomy: "unknown_alias", "unknown_modifier", "registry_inconsistency".

Step-by-step resolution with KV access pattern
Step 0 — Validation (zero KV reads)

Both alias and modifier are normalized to lowercase before any lookup
If alias is empty or the path has more than two segments: return { ok: false, status: 404, reason: "invalid_path" }
Reserved aliases (ig, youtube, spotify, c, api, nilufer) are rejected here too, though in practice Pages routing prevents them from reaching this handler
Step 1 — Parallel fan-out (1–2 KV reads, always parallel)

For both /<alias> and /<alias>/<modifier>, the alias record is always needed. When a modifier is present, the override key is also known immediately from the URL. Both can be fetched in a single Promise.all:

[alias_result, override_result] = await Promise.all([
  ALIAS_REGISTRY.get("alias:<alias>", { type: "json" }),
  modifier
    ? ALIAS_REGISTRY.get("alias_override:<alias>@<modifier>", { type: "json" })
    : Promise.resolve(null),
])

If alias_result is null → return { ok: false, status: 404, reason: "unknown_alias" }.

Step 2a — Override fast path (if modifier + override found)

If override_result is non-null:

canonical_slug = override_result.canonical_slug

Skip Step 2b and Step 3. Proceed directly to Step 4 (hub data fetch).

Step 2b — Campaign registry lookup (if no override)

campaign = await CAMPAIGN_REGISTRY.get("campaign:<campaign_id>", { type: "json" })

If campaign is null → return { ok: false, status: 500, reason: "registry_inconsistency" }. This is a data integrity failure (alias points to a campaign that has no registry entry) and must be logged as an operational alert, not surfaced as a 404.

Step 3 — Channel resolution (zero KV reads)

If modifier is absent:

channel_id = campaign.default_channel

If modifier is present:

channel_id = campaign.modifier_map[modifier]
if (channel_id === undefined) → return { ok: false, status: 404, reason: "unknown_modifier" }

The lookup is a direct property access on the in-memory object — O(1), no iteration.

Step 4 — Canonical slug construction (zero KV reads)

canonical_slug = campaign_id + "-" + channel_id

At this line the alias and modifier are dropped permanently. They are not stored, not logged to analytics, and not passed to any downstream function.

Step 5 — Hub data fetch (2 KV reads, parallel)

[slugRecord, config] = await Promise.all([
  LINKHUB_SLUGS.get(canonical_slug, { type: "json" }),
  LINKHUB_CONFIG.get("hub_config", { type: "json" }),
])

This is identical to what /c/:slug already does. If slugRecord is null or slugRecord.isActive === false, return a 404 response. Hub config is always fetched regardless (it's optional and gracefully absent).

Total KV read budget
Case	Round 1	Round 2	Round 3	Total
/<alias> (no modifier)	alias (1 read)	campaign registry (1 read)	slug + config (2 reads, parallel)	4 reads, 3 round-trips
/<alias>/<modifier>, no override	alias + override check (2 reads, parallel)	campaign registry (1 read)	slug + config (2 reads, parallel)	5 reads, 3 round-trips
/<alias>/<modifier>, override hit	alias + override (2 reads, parallel)	—	slug + config (2 reads, parallel)	4 reads, 2 round-trips
All lookups are direct-key gets. No list operations, no prefix scans, no iteration.

5. [alias].js and [alias]/[modifier].js — Handlers
Both handlers follow the same structure:

Parse alias (and modifier for the two-segment handler)
Call resolveAlias(alias, modifier, env) from alias-router.js
If result.ok === false: render the 404 hub page (same as existing not-found path) for status 404; return 500 for registry_inconsistency
Construct defaultUtms from slugRecord.defaults (same logic as /c/:slug)
Call resolveLinks(slugRecord, config) — unchanged from existing system
Call renderHub({ contextType: "campaign", contextId: canonical_slug, ... }) — identical parameters to /c/:slug; contextId is the canonical slug, not the alias
The response headers are identical to /c/:slug: Cache-Control: public, max-age=60.

The analytics path is unchanged: the client-side fireOutbound() will POST to /api/event with slug = CONTEXT_ID, which at that point is the canonical slug already embedded by the server into the JS payload.

Enforcement of the alias isolation invariant
The renderHub() call embeds contextId into the page's <script> block via JSON.parse(escJsString(...)). This value becomes CONTEXT_ID in the browser, and CONTEXT_ID is what the client sends to /api/event as the slug field. Since contextId is set to canonical_slug (not the alias), the invariant is enforced at the render boundary — there is no code path by which the alias enters the analytics payload.

6. Admin API Design
All endpoints require Authorization: Bearer <ADMIN_TOKEN> (same verifyToken() as existing API).

Alias endpoints — functions/api/alias/
Method	Path	Action
POST	/api/alias	Create new alias binding
GET	/api/alias/:alias	Read current binding + revision
PUT	/api/alias/:alias	Reassign alias (with optimistic lock)
DELETE	/api/alias/:alias	Detach alias
POST body:

{ "alias": "album", "campaign_id": "album-launch" }

Validates alias against reserved word list before writing. Sets routing_revision: 1.

PUT body (reassignment):

{
  "campaign_id": "album-v2",
  "expected_revision": 3,
  "reason": "New campaign cycle",
  "actor": "admin"
}

The handler reads the current binding, checks current.routing_revision === expected_revision. If mismatch → 409 Conflict. This is the optimistic lock that prevents concurrent writes from silently clobbering each other. On success: increment routing_revision, write new binding, write audit log entry.

Audit log entry (written to ALIAS_REGISTRY under a separate key prefix):

audit:<timestamp>-<alias>  →  {
  alias,
  previous_campaign_id,
  new_campaign_id,
  routing_revision,
  timestamp,
  actor,
  reason
}

Audit log keys use a timestamp prefix for chronological ordering and use the same ALIAS_REGISTRY namespace (they are operationally related but use a distinct key prefix that can be listed separately if needed). They are never written to LINKHUB_EVENTS or ROUTING_EVENTS.

Campaign registry endpoints — functions/api/campaign-registry/
Method	Path	Action
POST	/api/campaign-registry	Create campaign definition
GET	/api/campaign-registry/:id	Read campaign definition
PUT	/api/campaign-registry/:id	Update channels / modifier_map
The PUT validates that no channel is removed that still has an active alias binding pointing to it (prevents routing gaps). This requires reading all alias bindings that reference this campaign_id — but since alias records are small and this is an admin-only write path, a list operation is acceptable here (it is never on the hot serving path).

7. Operational Logging
Routing failures are logged via console.error() with structured JSON payloads. These appear in Cloudflare Workers Logs and can be piped via Logpush to any sink.

console.error(JSON.stringify({
  type: "unknown_alias" | "unknown_modifier" | "registry_inconsistency",
  alias,
  modifier: modifier || null,
  campaign_id: campaign_id || null,
  ts: Date.now(),
  path: request.url,
}))

If routing failure metrics need to be queryable (e.g., "how many unknown_modifier hits did /album/igx generate this week"), a second Analytics Engine dataset ROUTING_EVENTS can be bound and written using the same writeDataPoint() pattern as LINKHUB_EVENTS. This dataset is separate — it is an operational dataset, never mixed with click event analytics.

registry_inconsistency in particular is a data integrity alert (alias points to a non-existent campaign) and should be treated as a high-severity operational signal, not a normal 404.

8. Alias Reassignment Safety Model
Reassignment is the highest-risk operation. The model:

Optimistic lock via routing_revision: client reads current binding (GET), receives current routing_revision, sends it back as expected_revision on PUT. Server rejects if the value has changed since the read.
Audit trail: every reassignment writes an audit record before overwriting the binding, capturing previous state, new state, actor, reason, and timestamp.
Forward-only analytics: because historical analytics records only contain canonical slugs, reassigning alias:album from album-launch to album-v2 has zero effect on historical data. /c/album-launch-igbio records remain valid. Future hits resolve to /c/album-v2-igbio.
No cascade needed: reassignment only writes one KV key (alias:<alias>). All existing slug records, their analytics history, and their rendering configs are untouched.
9. Reserved Alias List
The alias creation endpoint must reject the following strings at write time:

ig, youtube, spotify, c, api, nilufer

These correspond to existing Cloudflare Pages Function route handlers. While Pages routing prevents dynamic [alias].js from handling those paths anyway, explicit rejection at the admin API level makes the constraint visible and prevents confusing mismatches between what can be registered and what can be served.
