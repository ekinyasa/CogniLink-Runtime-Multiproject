

# Prompt 39 — Enforce DECIDED Experiment Routing

## Context

The Campaign OS experimentation engine correctly detects and persists a winner:

state: DECIDED  
stored_winner: <variant>

However, routing still performs bucket assignment and continues A/B distribution even after the experiment is decided.

Observed behavior:

- `/api/experiments` returns:
  - state: DECIDED
  - stored_winner: <variant>

- Router responses still alternate between variants.

Example evidence:

ROUTE_DEFAULTS sometimes shows:

utm_variant = ab-test-1-spbio  
utm_variant = ab-test-1-igbio

This means the router ignores the decided state and still runs the bucket logic.

The system must enforce the stored winner when an experiment is decided.

---

## Goal

When an experiment reaches `DECIDED`:

- stop bucket assignment
- route **100% of traffic** to the stored winner
- maintain exposure tracking
- keep analytics intact

---

## Required Logic

Current routing logic (simplified):

```
resolveExperiment(alias)

if experiment exists:
    variant = bucketVisitor()
else:
    variant = default
```

Correct logic:

```
resolveExperiment(alias)

if experiment.state === "DECIDED":
    variant = experiment.stored_winner

else if experiment exists:
    variant = bucketVisitor()

else:
    variant = default
```

---

## Enforcement Rules

1. DECIDED experiments must **always return stored_winner**.
2. No further bucket assignment.
3. Exposure tracking should still record the chosen variant.
4. Analytics should continue aggregating normally.
5. Router must never return another variant once DECIDED.

---

## Expected Behaviour

Before decision:

```
ab-test-1-spbio
ab-test-1-igbio
```

After decision:

```
ab-test-1-igbio
ab-test-1-igbio
ab-test-1-igbio
```

No variant drift.

# Summary — Prompt 39 Implementation

## Root cause

DECIDED state was falling through to the `else` branch in `[[path]].js` (shared with RUNNING/PAUSED). This meant new visitors without a cookie were still assigned a random variant via `selectABVariant()`, causing traffic to split between variants even after a winner was stored.

## Fix

Single file changed: **`functions/[[path]].js`**.

Converted the two-branch `if / else` into a three-branch `if / else if / else`:

| Branch | Condition | Bucketing | Cookie | Counters |
|---|---|---|---|---|
| ARCHIVED | `expState === "ARCHIVED"` | bypass → `abConfig.winner` | no update | frozen |
| **DECIDED** (new) | `expState === "DECIDED"` | bypass → `abConfig.winner` | no update | continue |
| RUNNING / PAUSED | else | sticky cookie bucketing | set on new assignment | RUNNING: yes / PAUSED: frozen |

### DECIDED branch logic

```js
} else if (expState === "DECIDED") {
  const decidedWinner = (typeof abConfig.winner === "string" && abConfig.winner)
    ? abConfig.winner : null;
  finalSlug     = decidedWinner ?? canonicalSlug;
  newAssignment = false;
  utmExperiment = alias;
  utmVariant    = finalSlug;
  emitOps(env, OPS_EVENTS.AB_SELECTED, {
    alias, modifier: modifier ?? "", canonical_slug: finalSlug,
    campaign: deriveCampaignFromSlug(finalSlug), request_id: requestId,
    detail: { base_slug: canonicalSlug, variant_slug: finalSlug, sticky: false, state: expState },
  });
  context.waitUntil(incrementExpCounter(env, alias, finalSlug, "exposure"));
```

- `newAssignment = false` → no `Set-Cookie` header; no `Cache-Control: no-store`
- `decidedWinner ?? canonicalSlug` → safe fallback if winner field is somehow absent
- `incrementExpCounter` keeps running so analytics continue accumulating on the winner variant

### Updated inline comment block (routing section header)

```
// Sticky bucketing (RUNNING/PAUSED): ...
// DECIDED: cookie/bucket logic bypassed; 100% traffic → abConfig.winner.
//          No cookie update; exposure counters continue.
// ARCHIVED: same winner routing; exposure counters frozen too.
```

## Design decisions

- **Counters stay on for DECIDED**: analytics must keep accumulating so post-decision conversion data is valid. If counters were frozen, the winner's final conversion rate would be artificially low for any post-promotion analysis.
- **No cookie update for DECIDED**: the winner is deterministic (same for all visitors), so writing a cookie provides no benefit and would add unnecessary Set-Cookie overhead on every new visitor.
- **`decidedWinner ?? canonicalSlug` fallback**: guards against edge cases where `persistDetectedWinner` hasn't fired yet (e.g. if the experiment was manually forced to DECIDED via lifecycle API with no winner set). In that case the canonical slug is served as a safe no-op.
- **`sticky: false` in OPS event detail**: signals to any downstream analytics that this was a winner-enforced assignment, not a probabilistic bucket.
