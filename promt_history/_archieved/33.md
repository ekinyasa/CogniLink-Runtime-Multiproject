Prompt 33 — Experiment Analytics Layer (Exposure + Variant Metrics)

The system already has:

• Alias router
• Slug registry
• UTM injection
• A/B variant selection
• Admin panel for configuring A/B tests
• Structured ops telemetry events

Existing telemetry events:

alias_click
ab_selected
traffic_memory

These events already contain:

alias
canonical_slug
campaign
request_id

The goal of this prompt is to add a lightweight experiment analytics layer so the system can measure A/B test performance without relying on external analytics tools.

DO NOT modify the routing logic.

Only extend telemetry and aggregation.

⸻

OBJECTIVE

Implement an experiment analytics system with:
	1.	Variant exposure tracking
	2.	Variant click tracking
	3.	Experiment aggregation endpoint
	4.	Admin panel “Experiment Results” view

The system must remain lightweight and compatible with Cloudflare Workers.

⸻

SECTION 1 — Variant Identity

Currently analytics receives:

utm_variant=A
utm_variant=B

Replace this with semantic variant identifiers.

Instead of letters use the selected slug.

Example:

utm_experiment=abtest
utm_variant=cd26-test-yt

Rules:

• utm_experiment = alias
• utm_variant = selected variant slug

DO NOT remove any existing UTM parameters.

Append these two parameters to the final landing URL when A/B testing is active.

⸻

SECTION 2 — Telemetry Extension

Extend the existing traffic_memory event.

Current structure:

{
alias,
canonical_slug,
campaign,
request_id
}

Add fields when A/B is active:

experiment
variant

Example event:

{
ops_event:“traffic_memory”,

canonical_slug:“cd26-test-yt”,
campaign:“cd26-test”,
request_id:”…”,
detail:{
experiment:“abtest”,
variant:“cd26-test-yt”
}
}

This event represents variant exposure.

⸻

SECTION 3 — Click Tracking

Extend alias_click event to include experiment metadata.

SECTION 4 — Aggregation Endpoint

Create a new admin API endpoint.

GET /api/experiments?alias=

This endpoint aggregates telemetry events.

Return format:

{
experiment:“abtest”,
variants:[
{
slug:“cd26-test-igbio”,
exposures:421,
clicks:98,
ctr:0.232
},
{

exposures:398,
clicks:112,
ctr:0.281
}
]
}

Aggregation rules:

exposures = traffic_memory events
clicks = alias_click events
ctr = clicks / exposures

Data source can be:

• Worker logs
• KV counters
• R2 log drain

Prefer KV counters for simplicity.

⸻

SECTION 5 — KV Counter Model

Use deterministic counter keys.

Exposure counter:

exp:::exposure

Click counter:

exp:::click

Example:

exp:abtest:cd26-test-yt:exposure
exp:abtest:cd26-test-yt:click

Increment counters inside the telemetry emission logic.

1. How utm_experiment and utm_variant are appended

In functions/[[path]].js, after A/B variant selection:

  utmExperiment = alias;      // e.g. "abtest"
  utmVariant    = finalSlug;  // e.g. "cd26-test-yt"

These are written into defaultUtms before renderHub() is called:

  if (utmExperiment) defaultUtms.utm_experiment = utmExperiment;
  if (utmVariant)    defaultUtms.utm_variant    = utmVariant;

defaultUtms is serialised as ROUTE_DEFAULTS and injected server-side
into the hub page's <script> block. The client-side getMerged() merges
ROUTE_DEFAULTS with inbound URL params. buildHref() then appends all
merged keys (including utm_experiment and utm_variant) to every hub
link's destination URL — so GA4 / the landing page receives:

  ?utm_experiment=abtest&utm_variant=cd26-test-yt&...

This replaces the previous letter-based utm_variant=A/B/C scheme with
semantic slugs, giving direct traceability back to the A/B config.

──────────────────────────────────────────────────────────────────

2. How counters are incremented

Exposure counter (one per A/B-routed page view):
  — Incremented in functions/[[path]].js inside the abConfig block
  — context.waitUntil(incrementExpCounter(env, alias, finalSlug, "exposure"))
  — Fire-and-forget: does not block the hub response

Click counter (one per outbound link click on the hub page):
  — The hub's fireOutbound() now includes utm_experiment + utm_variant
    in its POST /api/event body
  — functions/api/event.js extracts these fields and calls:
    context.waitUntil(incrementExpCounter(env, expAlias, expVariant, "click"))
  — Only increments when both utm_experiment and utm_variant are non-empty

incrementExpCounter() in functions/_shared/exp-counter.js uses a
read-modify-write pattern: reads the current value, adds 1, writes back.
Not atomic but acceptable for typical campaign traffic (< 1k req/s).
Silent no-op on any KV error — analytics must never affect routing.

──────────────────────────────────────────────────────────────────

3. KV schema used for experiment metrics

Namespace: ALIAS_REGISTRY (reuses existing namespace — no new binding needed)
Key format: exp:<alias>:<slug>:<type>
Value:      plain text integer string (e.g. "421")

Examples:
  exp:abtest:cd26-test-igbio:exposure  →  "421"
  exp:abtest:cd26-test-igbio:click     →  "98"
  exp:abtest:cd26-test-yt:exposure     →  "398"
  exp:abtest:cd26-test-yt:click        →  "112"

Reads use { type: "text" } for minimal overhead.
Counter keys are deterministic — no listing or scanning required;
the aggregation endpoint reads exactly 2×N keys per experiment query
(one exposure + one click per variant), all in parallel.

──────────────────────────────────────────────────────────────────

4. How aggregation endpoint calculates CTR

GET /api/experiments?alias=<alias> in functions/api/experiments.js:

  1. Loads the A/B config via loadABConfig() (cached, no extra KV read)
  2. Extracts ordered variant slugs from config.variants[].slug
  3. Calls getExpCounters(env, alias, slugs) — reads 2N KV keys in parallel
  4. For each variant:
       exposures = parseInt(exp:...:exposure) || 0
       clicks    = parseInt(exp:...:click)    || 0
       ctr       = exposures > 0 ? round(clicks / exposures, 4) : 0
  5. Lift vs. baseline (first variant):
       lift[0] = 0  (baseline)
       lift[i] = (variantCTR - baselineCTR) / baselineCTR  (rounded to 4dp)
       lift[i] = null when baselineCTR === 0 (division by zero guard)
  6. Returns: { experiment, variants: [{slug, weight, exposures, clicks, ctr, lift}] }

──────────────────────────────────────────────────────────────────

5. How admin panel fetches experiment results

In functions/_shared/admin-renderer.js, new "Experiment Results" card
in the Routing tab (below the A/B Routing card):

  — loadAbAliases() now populates both #ab-alias-select AND #exp-alias-select
    from the same /api/admin/aliases response when the Routing tab first opens.
  — User selects an alias and clicks "Load Results"
  — loadExpResults() calls apiFetch("/api/experiments?alias=<alias>")
  — On success: renders a table with columns Variant / Traffic / Clicks / CTR / Lift
       • Lift column: "baseline" for first variant, green +X.X% or red -X.X% for others
       • null lift shown as — (baseline CTR was 0)
  — On error: shows inline error (e.g. "No A/B config for this alias.")
  — Button is disabled while loading, re-enabled on completion

# GPT Evaluation — Prompt 33 Review

Prompt 33 looks directionally strong. It extends the system into a real experiment analytics layer without touching the core routing engine, which is the correct architectural choice at this stage.

## What looks good

### 1. Semantic variant identity is the right move
Replacing `utm_variant=A/B` with the actual variant slug is the correct decision.

Why this is good:
- analytics becomes human-readable
- experiment debugging becomes easier
- no extra lookup table is needed later

Adding:
- `utm_experiment=<alias>`
- `utm_variant=<finalSlug>`

is exactly the right pattern.

---

### 2. Exposure vs click separation is correct
The implementation separates:
- exposure → on hub render / A/B routed page view
- click → on outbound click event

This is the right measurement model for lightweight experiment analytics.

---

### 3. KV counter model is simple and appropriate
Using deterministic keys like:

`exp:<alias>:<slug>:<type>`

is the correct tradeoff for this system.

Good aspects:
- no scans required
- fast reads for one experiment
- no extra storage binding needed

---

### 4. Aggregation endpoint design is sound
Loading the A/B config first, then reading exactly 2×N counters is efficient and predictable.

CTR and lift calculation rules are also sensible.

---

### 5. Admin panel placement is correct
Putting “Experiment Results” in the Routing tab is the right choice.
This is a routing/experiment concern, not a campaign-content concern.

---

## Weak / risky points to watch

### 1. Counter increments are not atomic
The summary explicitly says the counters use read-modify-write and are not atomic.

This is acceptable for low/moderate traffic, but it means:
- counts can drift slightly under concurrency
- experiment results are directionally useful, not audit-grade precise

This is not a blocker right now.

---

### 2. Exposure metric definition is page-view based
Exposure is counted when the A/B-routed hub is rendered, not when the outbound click happens.

This is a valid choice, but it means:
- exposures and clicks are measuring different stages of the funnel
- CTR is technically “hub click-through rate,” not final conversion rate

This is fine — just important to remember when reading results.

---

### 3. Existing analytics UI may still be confusing
The new experiment results card is likely much cleaner than the generic analytics tables, but we should verify the operator can actually interpret the numbers without ambiguity.

---

This implementation looks good enough to test directly.
No rollback signal is visible in the summary.
