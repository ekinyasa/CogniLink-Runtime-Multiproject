#Question to claude before promt 53
We recently implemented an Exposure Token System (Prompt 52).

The experiment router now generates a signed token and returns:

{
  finalSlug,
  variantId,
  isNewAssignment,
  cookieToSet,
  expToken
}

In [[path]].js we attach it to the default UTMs:

defaultUtms.exp_token = expResult.expToken;

The hub page is rendered using renderHub() and client-side links are built by buildHref() in hub-renderer.js.

However, in production we observe that exp_token never appears in generated links.

Example rendered link:

https://niluferormanli.com/?utm_source=tiktok&utm_medium=bio&utm_experiment=abrand45&utm_variant=ab-rand-45-ttbio&utm_campaign=ab-rand-45&utm_content=primary_official

Notice exp_token is missing.

We suspect buildHref() is filtering query parameters.

Please inspect the code and answer:

1. Where exactly are hub link URLs assembled?
2. Does buildHref() whitelist allowed parameters?
3. Is exp_token being dropped during URL assembly?
4. What is the minimal change required so exp_token propagates exactly like other utm_* parameters?

Do not implement a fix yet.

Only:
- show the relevant code paths
- explain where exp_token is lost
- propose the safest minimal fix.


#ANSWER:
Here is the full code-path audit. No code is changed — this is analysis + proposal only.

---

## 1 — Where exactly are hub link URLs assembled?

Two stages, both in the same request cycle:

**Server-side — `[[path]].js` lines 299–313**
```js
const defaultUtms = Object.assign({}, slugUtms, storedUtms);   // line 302
if (utmExperiment) defaultUtms.utm_experiment = utmExperiment; // line 304
if (utmVariant)    defaultUtms.utm_variant    = utmVariant;    // line 305
if (expResult?.expToken) defaultUtms.exp_token = expResult.expToken; // line 309
```
`defaultUtms` is then passed into `renderHub()`, which JSON-serialises it at **hub-renderer.js line 34**:
```js
const utmsJson = JSON.stringify(defaultUtms);
```
…and embeds it as a JS literal at **line 177**:
```js
var ROUTE_DEFAULTS = JSON.parse('${escJsString(utmsJson)}');
```

**Client-side — hub-renderer.js lines 299–308**
On DOMContentLoaded, every `<a>` is wired at line 302:
```js
el.href = buildHref(meta.href, meta.utmContent, meta.noUtm);
```
`buildHref()` calls `getMerged()` (line 244), then iterates over every key in the result (lines 247–252) and appends them to the destination URL.

---

## 2 — Does `buildHref()` whitelist allowed parameters?

**No whitelist exists.** Lines 247–252:

```js
Object.keys(merged).forEach(function (k) {
  var v = merged[k];
  if (v && !url.searchParams.has(k)) {
    url.searchParams.set(k, String(v));
  }
});
```

Every key whose value is truthy and that is not already present on the destination URL is appended. `exp_token` is not named anywhere in `buildHref()` or `getMerged()`. It would pass through without modification — **if it were present in `merged`**.

The UTM-cleanup block (lines 238–242) only removes `utm_*` keys from the **destination** URL. It does not touch non-`utm_` keys. `exp_token` would survive that step untouched.

---

## 3 — Is `exp_token` being dropped during URL assembly?

Not by `buildHref()`. The drop happens **before the HTML is even rendered**, at `[[path]].js` line 309:

```js
if (expResult?.expToken) defaultUtms.exp_token = expResult.expToken;
```

`expResult.expToken` is **`null`**, so this guard is never satisfied, `exp_token` never enters `defaultUtms`, it is absent from `utmsJson` → absent from `ROUTE_DEFAULTS` → absent from `getMerged()` → `buildHref()` has nothing to append.

The observed link confirms this: `utm_experiment` and `utm_variant` are present (they have unconditional guards — lines 304–305 use `if (utmExperiment)` which is set whenever `abActive === true`). `exp_token` has a **conditional guard that depends on `expResult.expToken` being truthy** — and it is not.

The path from `expResult.expToken` back to the source:

```
[[path]].js:246 → resolveExperimentVariant()
experiment-router.js:163 → generateExposureToken(alias, finalSlug, env)
exposure-token.js:103 → const secret = env?.EXPOSURE_TOKEN_SECRET;
exposure-token.js:104 → if (!secret) return null;
```

`generateExposureToken` returns `null` immediately when `EXPOSURE_TOKEN_SECRET` is not bound. That propagates all the way up as `expResult.expToken = null`, the guard at line 309 is skipped, and `exp_token` is never added to `defaultUtms`.

There is also a secondary `sessionStorage` observation worth noting: `TRACKING_KEYS` (hub-renderer.js lines 183–186) does not include `exp_token`, so inbound tokens from the hub page URL are not saved to `sessionStorage.tracking_context`. This is correct by design — each hub page render should generate a fresh token. However, it does mean that if `exp_token` were somehow present in the hub page URL as an inbound parameter (not the current flow), it would not be carried forward via sessionStorage. This is a non-issue for the current architecture where the token originates exclusively from `ROUTE_DEFAULTS`.

---

## 4 — Minimal change required

**The fix is infrastructure, not code.** `buildHref()` requires zero changes.

The required action is to bind `EXPOSURE_TOKEN_SECRET` in the Cloudflare environment:

```toml
# wrangler.toml — or set via the dashboard / `wrangler secret put`
[vars]
EXPOSURE_TOKEN_SECRET = "..."
```

Once bound, the call chain is:
1. `generateExposureToken()` returns a real token instead of `null`
2. `expResult.expToken` is truthy
3. Line 309 guard passes → `defaultUtms.exp_token = expResult.expToken`
4. `renderHub()` serialises it into `ROUTE_DEFAULTS`
5. `getMerged()` returns it in `merged`
6. `buildHref()` appends `?exp_token=<base64url>.<base64url>` to every hub link

**No code changes are needed in `buildHref()`, `hub-renderer.js`, `experiment-router.js`, or `[[path]].js`.** The implementation is correct end-to-end; the secret is simply not set in the environment.

---

### One design note to be aware of before enabling

The same `exp_token` is embedded in **all links** on a single hub render. The nonce replay key (`exp_used:<nonce>` in KV) is consumed on the first successful `/api/convert` call. A user who clicks two separate links from the same hub render and both landing pages fire conversions will have the second one rejected with `token_already_used`. This is likely intentional (one conversion per exposure event), but worth confirming before you set the secret in production.

# Prompt 53 — Bandit Cron Scheduler (Adaptive Traffic Weights)

You are working inside the Campaign OS Cloudflare Workers codebase that powers the Nilüfer Ormanlı campaign routing and experiment engine.

Previous steps:

Prompt 51 → Experiment Router Extraction  
Prompt 52 → Exposure Token System (conversion integrity)

Now we implement **automatic traffic rebalancing** using a simple bandit scheduler.

This must run **outside the request path** so user traffic latency stays unchanged.

IMPORTANT: This is not a full ML system.  
We want a **deterministic, transparent, low-risk bandit adjustment**.

---

# Goal

Allow running experiments to **adapt weights gradually** based on performance.

The system should:

- periodically evaluate experiment performance
- slightly increase traffic to better variants
- slightly decrease traffic to worse variants
- never fully starve a variant
- remain explainable and stable

---

# Architecture

A scheduled Worker (cron trigger) will run periodically.

Example interval:

```
*/10 * * * *
```

(every 10 minutes)

The scheduler will:

1. load all experiments
2. filter experiments with `state === "RUNNING"`
3. compute performance metrics
4. adjust weights
5. write updated weights back to KV

---

# Metrics to Use

Each variant already stores:

```
exposures
clicks
conversions
ctr
conversion_rate
```

Use **conversion_rate** as the primary signal.

Minimum data threshold before learning:

```
exposures >= 50
```

Variants below threshold keep current weight.

---

# Weight Adjustment Algorithm

Simple soft bandit rule:

```
score = conversion_rate
normalized_score = score / sum(scores)

new_weight = clamp(
    round(normalized_score * 100),
    MIN_WEIGHT,
    MAX_WEIGHT
)
```

Constants:

```
MIN_WEIGHT = 10
MAX_WEIGHT = 80
```

This prevents starvation and preserves exploration.

Weights must always sum to **100**.

If rounding breaks the sum, adjust the largest variant.

---

# Safety Rules

Never adjust if:

```
experiment.state != "RUNNING"
```

Never adjust if:

```
total_exposures < 200
```

Never allow:

```
weight < MIN_WEIGHT
```

Never allow:

```
weight > MAX_WEIGHT
```

---

# Files to Add

Create a scheduler module:

```
/functions/cron/bandit-update.js
```

It should:

- iterate experiments
- compute new weights
- update KV experiment config

---

# Worker Integration

Add a cron handler in the Worker:

```
export default {
  async scheduled(event, env, ctx) {
    await runBanditUpdate(env);
  }
}
```

Ensure this runs independently of normal HTTP routing.

---

# Observability

Log adjustments:

```
console.log("BANDIT_UPDATE", {
  experiment,
  old_weights,
  new_weights
})
```

This keeps the system auditable.

---

# Required Output

Provide:

1. bandit-update.js implementation
2. cron handler integration
3. example weight update log
4. confirmation that no request-path latency is added

Do NOT modify experiment routing logic.

The bandit system must remain **separate from the request router**.

---

## Implementation Summary

### Files Created

**`functions/cron/bandit-update.js`**

Three internal units:

`computeSoftBanditWeights(variants, counters)` → `number[] | null`
- Builds a `counterMap` keyed by slug for O(1) lookup
- **Per-variant gate**: if any variant has `exposures < MIN_VARIANT_EXPOSURES` (50), returns `null` — the whole experiment keeps its current weights
- Computes `scores[i] = conversion_rate` for each variant
- `totalScore = sum(scores)`
- If `totalScore === 0` (no conversions yet): distributes evenly using the largest-remainder method (integer sum = 100 guaranteed)
- Otherwise: `new_weight[i] = clamp(round(scores[i] / totalScore × 100), MIN_WEIGHT, MAX_WEIGHT)`
- Sum fix: if rounding makes sum ≠ 100, adjusts the largest-weight variant by the residual ±diff (re-clamped)
- Constants: `MIN_WEIGHT = 10`, `MAX_WEIGHT = 80`

`tryUpdateExperiment(env, alias)` → `Promise<boolean>`
- Reads `ab_config:<alias>` directly from KV (bypasses in-memory cache — cron always sees fresh data)
- Safety rule 1: `getExpState(config) !== "RUNNING"` → return false
- Safety rule 2: `totalExposures < MIN_TOTAL_EXPOSURES` (200) → return false
- Safety rule 3: enforced by `computeSoftBanditWeights` returning null
- No-op skip: if computed weights equal current weights, no KV write
- Observability log: `console.log("BANDIT_UPDATE", JSON.stringify({ experiment, old_weights, new_weights }))`
- Merges new weights into config (preserves all other fields: state, winner, created_at, etc.)
- Writes updated config to KV
- Invalidates in-memory cache via `cacheDelete("ab_cfg:<alias>")` so the router picks up new weights within one TTL cycle (≤ 60 s)

`runBanditUpdate(env)` → `Promise<void>` *(exported)*
- Guards on `env.ALIAS_REGISTRY` presence
- Paginates through all `ab_config:*` keys using KV `list()` with cursor loop
- Calls `tryUpdateExperiment` for each alias **sequentially** (avoids KV write quota burst)
- Logs run summary: `[bandit-cron] run complete { experiments_scanned, experiments_updated }`

### Files Modified

**`wrangler.toml`**
- Added `[triggers]` comment block at the end of `[env.production.vars]` with:
  - Cron expression: `*/10 * * * *`
  - `_worker.js` integration pattern shown in comments
  - `[triggers] / crons` block commented out — uncomment once the scheduled handler is wired

### Cron Handler Integration

The `scheduled` handler is not enabled by default (Cloudflare Pages Functions do not support cron triggers via the `functions/` directory). Once ready to activate:

1. Add `_worker.js` to the project root (Pages advanced mode) or deploy a standalone Worker:
   ```js
   import { runBanditUpdate } from "./functions/cron/bandit-update.js";
   export default {
     async fetch(request, env, ctx) { /* delegate to Pages Functions routing */ },
     async scheduled(event, env, ctx) {
       ctx.waitUntil(runBanditUpdate(env));
     },
   };
   ```
2. Uncomment `[triggers]` in `wrangler.toml`.

### Request-Path Latency Impact

**Zero.** `runBanditUpdate` is called exclusively from the `scheduled` event handler, which is invoked by Cloudflare's cron infrastructure on a separate execution context — never during an HTTP request. The router (`[[path]].js` → `experiment-router.js`) does not call or import this module. New weights are picked up passively when the in-memory TTL cache expires (within 60 s of the KV write).

### Algorithm vs. Thompson Sampling (Prompt 48)

| | Cron (Prompt 53) | Admin endpoint (Prompt 48) |
|---|---|---|
| Trigger | Automatic, every 10 min | Manual `POST /api/experiment/bandit-update` |
| Algorithm | Soft-bandit: normalized conversion rate | Thompson sampling: Beta(α, β) with N=200 draws |
| Determinism | Deterministic per run | Stochastic (averaged, but not perfectly repeatable) |
| Auto-archive | No | Yes (14-day inactivity window) |
| Alpha/beta update | No (weights only) | Yes (writes alpha/beta metadata) |

Both update `variant.weight` in the same `ab_config:<alias>` KV record. The router always reads only `variant.weight`.
