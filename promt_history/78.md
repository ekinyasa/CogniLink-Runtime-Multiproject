# ✅ Diagnosis — P78

## TL;DR

Your hypothesis is **partially correct but misidentifies the scope**. The write path (computeEpsilonWeights → KV) does exist — it was implemented in P71. The real problem is narrower: **the conversion trigger is missing**, and the only active trigger fires with 1/500 probability, which never fires during manual browser testing.

---

## A. Hypothesis validation

| Claim | Verdict | Detail |
|---|---|---|
| `computeEpsilonWeights` never called at runtime | ❌ Wrong | Called inside `maybeRebalance`, which IS wired to `[[path]].js` |
| No active decision loop | ❌ Wrong | Loop exists: `maybeRebalance` checks data, computes weights, writes KV |
| No KV write for updated weights | ❌ Wrong | `CAMPAIGN_REGISTRY.put("ab_config:<alias>", ...)` is in place (P71) |
| Router uses static/initial weights | ❌ Wrong | `loadABConfig` reads from `CAMPAIGN_REGISTRY` which is what `maybeRebalance` writes to |
| System behaves as read-only bandit | ✅ Correct for the conversion path | `t.js` (the conversion handler) does NOT call `maybeRebalance`. Only increments counters. |

## B. Actual root causes (ranked by impact)

### RC1 — Missing conversion trigger (highest impact)

`t.js` receives all conversion events at `/t?e=conversion`. It correctly writes to `TELEMETRY_REGISTRY` via `incrementExpCounter`. But it **never calls `maybeRebalance`**.

The JSDoc comment at the top of `bandit-rebalance.js` already documents the intent:
```
 * Trigger points (wired by callers):
 *   • conversion.js  → waitUntil(maybeRebalance(env, alias, "conversion"))
 *   • [[path]].js    → probabilistic exposure boundary (~1/500 chance per hit)
```

The first trigger point — `conversion.js` — was designed but never wired. In this codebase, that handler is `t.js`. The call is absent.

**Effect:** conversions accumulate in TELEMETRY_REGISTRY, the admin panel shows them, `detectLeadingVariant` can read them — but nothing triggers the rebalance. Panel says "winner found"; weights say 50/50.

---

### RC2 — 1/500 exposure trigger doesn't fire in manual tests (medium impact)

The only active trigger is in `[[path]].js`:
```js
if (expResult.counterPromise && abConfig.strategy !== "fixed" && Math.random() < 0.002)
  context.waitUntil(maybeRebalance(env, alias, "exposure"));
```

`0.002 = 1/500`. To have a 63% chance of seeing this fire once, you need ~500 page loads on the same experiment. With manual browser testing (10–30 loads), the probability of triggering even once is 2–6%. The trigger almost certainly never fires.

This is not a bug — it's intentional amortization. But it makes the system appear broken in low-traffic manual tests.

---

### RC3 — Stability layer gates (P76) may further block rebalance (lower impact)

Even if the trigger fires, `detectLeadingVariant` now requires:
- `conversions >= 3` per variant (P76)
- `|delta_abs| >= 0.005` OR `delta_rel >= 0.20` (P76)

In a manual test with artificially injected conversions, the delta thresholds are likely met. But the conversion count gate (`>= 3` per variant) may block if one variant has fewer than 3 real conversions.

This is working as designed — but it is worth knowing it can absorb tests that look like they should trigger a rebalance.

## C. Factors you didn't mention

**In-memory cooldown (Guard 1) survives within an isolate:**
If `maybeRebalance` fires once and sets the 5-minute in-memory cooldown, it cannot fire again from the same isolate during that window. In a browser test session, this could hide follow-up rebalances.

**Preview environment vs production:**
`wrangler.toml` has separate `[env.preview]` bindings for `CAMPAIGN_REGISTRY` and `TELEMETRY_REGISTRY`. If testing in Cloudflare preview while data is written to production KV namespaces (or vice versa), the bandit reads a different `ab_config` than where conversions are written. The panel and the router could be looking at different data sources.

**`ab_config` cache (`ab_cfg:` prefix):**
`loadABConfig` caches results in-memory (kv-cache.js). If the bandit writes a new `ab_config` to KV but the router's in-memory cache hasn't expired yet, the router continues using the stale weights. This is by design (up to 60s lag), but during a short manual test it means weight updates are invisible immediately after rebalance.

## D. Planned fix assessment

Your plan:
> Real decision loop + KV-based weight persistence + router reads from KV + unified routing paths

**Verdict: already implemented (P71–P77).** The architecture you describe is exactly what exists. There is no fundamental design flaw. The missing piece is narrow:

**One missing wire: `t.js` should call `maybeRebalance` when `e === "conversion"`.**

That's it. No new files needed. No architecture change. The `context.waitUntil(maybeRebalance(env, alias, "conversion"))` call belongs inside the existing `if (e === "conversion")` block in `t.js` — but it needs `alias` from the query params (which `t.js` already reads and sanitizes).

**The conversion trigger in `t.js` needs `alias`** (the experiment alias, not the variant slug). `t.js` already accepts `alias` as a query param for the breakdown counters. So the wire is: when `e === "conversion"` and `alias` is present, also call `maybeRebalance(env, alias, "conversion")`.

## E. Is there a simpler architecture?

No. The current architecture is already minimal:
- One KV key per experiment (`ab_config:<alias>`)
- One function computes weights (`computeEpsilonWeights`)
- One function guards + writes (`maybeRebalance`)
- One function reads for routing (`loadABConfig`)
- Two trigger points (exposure boundary + conversion)

The only gap is the missing second trigger point. Adding it is a one-liner inside an existing conditional.
