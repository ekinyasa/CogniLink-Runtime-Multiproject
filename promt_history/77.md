

# Prompt 77 — Exploration Floor (Do NOT kill learning)

We now have a working epsilon-greedy bandit with:

- Minimum exposures ✔️
- Minimum conversions ✔️
- Delta threshold (abs + relative) ✔️
- Cooldown ✔️

However, the system still has a **critical long-term failure mode**:

→ It can **collapse exploration too aggressively** and stop learning.

---

## 🎯 Problem

When a winner is detected, current behavior:

- Winner → ~90%
- Loser → ~10% (or potentially lower in future logic)

If this ever becomes:

- Winner → 98%
- Loser → 2%

Then:

- Loser stops receiving meaningful traffic
- No new data is collected
- System becomes **locked into early decisions**
- Cannot recover from wrong winner

---

## 🎯 Goal

Guarantee that **every variant always receives minimum traffic**.

This is called:

→ **Exploration Floor**

---

## 🧠 Rule

Define a constant:

```
MIN_WEIGHT_FLOOR = 0.1
```

Meaning:

- No variant can go below **10% traffic share**

---

## 🔧 Implementation Scope

Modify ONLY the weight assignment logic inside:

→ `maybeRebalance(...)`

Do NOT change:

- routing
- epsilon logic
- detectLeadingVariant
- cooldown logic

---

## 🔧 Required Behavior

After computing weights:

1. Identify winner and loser
2. Apply floor:

```
loser_weight = Math.max(computed_loser_weight, MIN_WEIGHT_FLOOR)
winner_weight = 1 - loser_weight
```

3. Ensure:

- weights sum to 1 (or 100 depending on system)
- no variant < MIN_WEIGHT_FLOOR

---

## ⚠️ Edge Cases

If multiple variants exist (future case):

- Apply floor to ALL non-winners
- Re-normalize remaining weight to winner

# ✅ Implementation — P77

## File changed

`functions/_shared/bandit-rebalance.js` — one new constant + T4 block inside `maybeRebalance` only.

## New constant

```js
/** Minimum traffic allocation for any non-winner variant (P77).
 *  Prevents learning collapse: even a clear loser keeps receiving traffic so
 *  the system can detect if performance improves. */
const MIN_EXPLORE_FLOOR_PCT = 10;   // 10 % — currently equal to EXPLORE_BUDGET for 2 variants
```

## Updated T4 block in `maybeRebalance`

```js
const rawWeights  = computeEpsilonWeights(config.variants, detection.winner);
const winnerIdx   = config.variants.findIndex((v) => v.slug === detection.winner);
const newWeights  = rawWeights.map((w, i) => (i !== winnerIdx ? Math.max(w, MIN_EXPLORE_FLOOR_PCT) : w));
const explorerSum = newWeights.reduce((s, w, i) => (i !== winnerIdx ? s + w : s), 0);
newWeights[winnerIdx] = 100 - explorerSum;
```

## What changed

- `computeEpsilonWeights` produces raw weights (unchanged).
- Non-winner slots are clamped to `Math.max(w, 10)` — floor applied.
- `newWeights[winnerIdx]` is recalculated as `100 - explorerSum` so the total always sums to 100 with no rounding drift.
- In the current 2-variant case the floor has no numeric effect (loser already gets 10) — but it becomes load-bearing the moment `WINNER_WEIGHT` is raised or a third variant is added.
- `detectLeadingVariant`, cooldown logic, KV schema, routing — all untouched.
